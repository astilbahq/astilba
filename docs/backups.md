# Backups, scheduled jobs and fresh restores

The deployment agent sends encrypted backup data directly to a workspace destination. The management database stores policies and bounded run history, not customer database dumps. A completed upload is **unverified** until a fresh restore passes its recipe checks. Preparing cutover creates a draft revision; the existing deployment-plan review is still required before traffic or storage changes.

## Supported recipes

| Source | Consistency and verification | Limits |
| --- | --- | --- |
| Managed PostgreSQL 17.10 or 18.4 | Native custom-format logical dump; restore roles and recreate the database in a new volume; compare canonical SQL/data and database metadata from a second dump | The pinned PostgreSQL images and their version-specific layouts; one managed database; `plpgsql` and `hstore`; additional roles must be unprivileged NOLOGIN roles without memberships or cluster-wide role settings |
| Named file volume | Stop every declared container using the volume, reject unknown users, archive stable files, resume writers; extract into a new volume and compare its archive | Local Docker volumes with regular files, directories and symbolic links (up to 100,000 entries); all writers must be visible to this Docker daemon. Hard links and special files require another recipe. Directory timestamps are excluded from restore comparison. Do not use this recipe to claim a live database copy is consistent |
| Scheduled container job | Run an explicit argument array using an applied image worker's environment and mounts, on exactly the worker's networks without its network aliases; record its exit code | Visual image workers; never a privileged or added-capability service or one that shares a named volume or network with such a service; fixed resource bounds; missed runs are skipped; arbitrary job replay is never automatic |

PostgreSQL uses [the pinned deployment image](../services/platform/internal/domain/visual.go). The agent dumps a database from a helper container labelled with the run, made from the database's own pinned image so its `pg_dump` matches the server. The helper shares the database container's network namespace and connects over TCP with the stored credential, which it receives only in each command's environment, so Docker never shows it. Nothing runs inside the database container itself. A database whose image is no longer one of the pinned images is refused, never dumped with another image. Restic is pinned to **0.19.1**. The agent advertises backup support only when that version and the deployment prerequisites are present. Install the binary from the [official release](https://github.com/restic/restic/releases/tag/v0.19.1), verifying its checksum; the disposable test installer is [backup-tools.sh](../services/platform/host/backup-tools.sh).

The encrypted agent journal retains the database initialization credential, so fresh recovery can proceed when the source container is stopped or missing. Existing source resources are still checked for ownership.

PostgreSQL recovery includes database ownership, permissions, comments, connection limits and database-specific settings, including settings for roles within that database. Existing custom-format snapshots already contain this metadata. The agent uses `pg_restore --create` and includes database creation in its comparison with the restored dump. Database creation cannot run inside a transaction, so restoration stays in an isolated fresh cluster; a failed restore never becomes a verified cutover target. See [PostgreSQL's restore options](https://www.postgresql.org/docs/18/app-pgrestore.html).

A policy freezes its applied deployment. After a deployment changes, refresh the policy and install its new generation before expecting further backups. A failed source check does not silently back up a different resource. A new source, destination or consistency method requires a new policy.

## Destination setup

Owners with recent account verification can create reusable destinations. Credentials and repository passwords are write-only and encrypted in the management database and the agent journal. Keep the repository password and storage credentials in independent recovery records. Losing both those records and the agent's protected state makes encrypted snapshots unrecoverable.

- **S3 compatible:** provide an HTTPS origin, existing bucket, region and access credentials. Allow the agent to reach that origin. Each repository uses `astilba/<workspace UUID>/<policy UUID>` within the bucket. Customer private endpoints are contacted by the deployment agent, never fetched through the management service.
- **Filesystem:** create a real, private directory on the deployment server and enable its exact path with `--backup-roots`. The agent creates `<workspace UUID>/<policy UUID>/repository` and a separate ownership marker. Symlinked roots are rejected. This destination shares the server's failure boundary unless the operator provides independently durable mounted storage.

For the systemd installation, use a drop-in appropriate to the selected paths, for example:

```ini
[Service]
ExecStart=
ExecStart=/usr/local/bin/astilba-agent run --restic-cli /opt/astilba-platform-tools/restic --backup-roots /srv/backups
ReadWritePaths=/srv/backups
```

The root must already exist with suitable permissions. The agent's existing state directory remains private. A destination check opens the repository and validates its identity; installing a new policy initializes its separate encrypted repository. No shared repository pruning is used.

An S3 destination is exposed while a revoked server holds its storage keys: the server a policy using it is bound to, or one a restore of such a policy was recorded for. That server can still delete or overwrite whatever the keys reach until they are revoked at the provider. A filesystem destination has no keys, and a container job is never given any. Destinations report it as `exposed`, with the policies using each. The dashboard warns on every policy on an exposed destination, creating a policy on one needs `exposureAcknowledged`, which is audited as `backup.destination.exposure.acknowledge`, and one [`backup_exposure` alert](operational-alerts.md#detection-and-recovery) fires for the destination. Destinations can't be edited, so a destination stays exposed until each of those servers is renewed, even once its keys are revoked. Add a destination with new keys for backups a revoked server can't reach.

## Scheduling, retention and interruptions

Choose daily, cron or fixed-interval schedules. An existing daily policy keeps its original schedule representation and digest, including an empty timezone interpreted as UTC.

| Schedule | Timing |
| --- | --- |
| Daily | A local hour/minute in an IANA timezone, such as `Europe/London`. |
| Cron | Five fields: minute, hour, day of month, month, weekday. Supports lists, ranges, steps and month/weekday names; weekdays are 0–6 (Sunday–Saturday). `0 2 * * MON-FRI` runs at 02:00 on weekdays. Restricted day-of-month and weekday fields use OR semantics. No seconds, `@` shortcuts or embedded timezone prefixes. |
| Fixed interval | 1–525600 elapsed minutes, anchored to the first installed UTC instant. The first run is one interval after installation; later runs do not drift with job duration or daylight-saving changes. A new installed generation resets the anchor. |

Daily/cron schedules skip nonexistent local times and choose the first occurrence of a repeated wall-clock minute, including half-hour transitions. Cron expressions require an explicit IANA timezone; interval schedules use UTC. Calendar lookup uses the pinned parser's five-year look-ahead; an unavailable next occurrence blocks installation or execution instead of spinning or guessing.

The dashboard formats next runs in the configured timezone. If that zone is unavailable in the browser, it labels a UTC display without changing the schedule.

A job's command could drive a privileged service that its source shares a named volume or a network with, so management refuses to save or run a job whose source deployment review treats as elevated, and the agent refuses it again before each run, also checking the containers the daemon runs beside the source. The job container joins the same networks as the source container, each of which must belong to the deployment, or none if the source has none.

Each run's identity includes policy ID, generation and scheduled UTC instant. The agent persists the next instant together with its run record before host effects. Restart, reconnect and backward clock changes cannot replay an admitted run. Forward clock changes follow the missed-run rules: missed backups coalesce into one catch-up for the latest due instant, while container jobs more than one minute late are skipped with a history record. There is no arbitrary job replay or configurable parallelism.

Jobs and backups share the host execution lock with deployments and upgrades. If the host is busy, the same catch-up/skip rules apply when it becomes available. Installed schedules continue while management is unavailable; bounded reports upload when it returns. Disabling a local schedule requires delivery to that agent. Installing or disabling a schedule commits it together with its command's outcome, checking a repository changes nothing, and each step of creating a repository can be repeated, so an agent stopped during one of these runs it again rather than holding the host's schedules for inspection. One run again after its deadline ends cancelled with no schedule changed, except an install that had begun creating its repository, which may run again until its lifetime after the agent first started it. If the agent stopped while writing a new repository's ownership marker, the install fails as a mismatch rather than adopt the directory.

Upload/job timeouts can be set from 1 to 1800 seconds; omission preserves the thirty-minute limit. Restores retain their separate thirty-minute limit. A backup or restore command's lifetime is its run's limit plus ten minutes, and never less than thirty minutes. It may start until that long after management issues it, its deadline, and once the agent starts it, after any wait behind other work on the host, it may run for that long. So a run that runs long ends by its own limit rather than by its command's bound, and a run-now backup queued behind a long scheduled run still gets its whole lifetime. A command that reaches the host after its deadline, for example because its agent was offline, never starts, and management no longer sends its repository access. A timed-out job stops and removes only its owned run container, with up to thirty additional seconds to confirm cleanup and record the exit result. A timeout is never evidence of successful application work.

General schedules and custom timeouts require an updated agent advertising the negotiated `schedules` capability. Extended commands use the `schedule` kind, which older executors reject before effects. Current agents omit this capability when talking to older management schemas. The management database advances to schema 17 and older management binaries refuse startup against it.

Advanced schedules remain encrypted in a versioned agent journal bucket, alongside a disabled legacy mirror of their run/writer fences. A rolled-back agent cannot run their cadence, but can still recover recorded writers and block operations over unresolved runs. After an older agent changes or resolves that state, the newer agent honors its newer generation/sequence rather than resurrecting hidden advanced work. The dashboard shows the effective disabled state; save and install a new policy generation to resume general scheduling. Controller transfer preserves policy IDs, history and interval cursors and still refuses unresolved effects.

Retention considers only this policy's catalogued snapshots after a successful upload. It keeps the configured recent uploads, the newest demonstrated recovery point and the snapshot of any restore that is running or unresolved. A restore that ends, whether it succeeds, fails or is resolved, releases its snapshot. Unknown snapshots are left alone. Maintenance has a bounded repack size and operation deadline. Restores have a thirty-minute execution limit; upload/job limits are described above. Full manifests stay in the encrypted repository; operational records carry their hash and compact metadata. History is bounded to 128 records per policy while retaining a representative of each available snapshot; redundant completed restore records can age out. History keeps the run that uploaded each available snapshot rather than a restore of it. Unresolved protected history can require operator attention instead of being silently discarded.

An interrupted run does not become a success. A run stopped before its first effect fails. One that fails or is stopped after it began changing things, by a cancel, its command's bound, its own limit or the agent stopping, fails only once its cleanup is confirmed: every container labelled with the run (its dump or data helper, restore database or job) is removed, which ends whatever ran in it (a database connection it held ends within a second), and restic has exited. Otherwise the run and its command need attention, and the run's note names what could not be confirmed, such as a container Docker would not remove. So does a run the agent was killed or crashed during, which nothing could clean up. A run that fails leaves no usable record: a snapshot restic uploaded before the run stopped stays uncatalogued, and a restore's target volume is retained. Inspect any containers with the run's `com.astilba.run` label and the retained target volume. Once uncertain containers are stopped and the outcome is understood, a local operator can close the failed run:

```sh
astilba-agent resolve-run --policy POLICY_UUID --run RUN_UUID
```

This resumes recorded file writers where their identity still matches, refuses active run containers, and records failure rather than claiming a valid backup. It also records the run's own command as failed. Any other operation the host refused while the run was unresolved still needs `astilba-agent retry`. The operator can then retry a new run. A restore's snapshot stays protected until its run is resolved. A run under a coordinated reservation is resolved with `astilba-agent reject-cross-host-effect` instead; see [Cross-host placement](cross-host-placement.md). Existing application data is never deleted by these operations.

A restore of a lost server's snapshot onto its replacement uses the `restore` command kind, which only an agent advertising `recoveryRestore` receives: an older agent would hold the command unsettled. The replacement holds no schedule for the lost server's policy. It reads only the manifest and the archive file beside it out of the snapshot, and no more of the archive than the manifest gives as its size. Before creating anything it refuses a snapshot not written for the policy's environment, resource and method, one holding other than exactly one manifest with an archive file beside it, an archive that differs from its manifest, a database archive made with an image Astilba doesn't pin or for another database or owner than the deployment's, or a target volume the deployment declares. The database password comes from the replacement's own PostgreSQL container. The restore's own container has no network, can't gain privileges and mounts only its target volume. A database restore runs as `postgres` with no capabilities, and a file restore keeps only those that restoring owners and modes needs. The archive reaches it only through standard input. A restore stopped after it began creating its target fails once nothing labelled with its run is still running. Otherwise it needs attention, without the repository's access, until `resolve-run` with the lost server's policy and the run settles it.

## Snapshot receipts

A server reports its own times for the snapshots it uploads, and a host that was compromised can backdate them. A snapshot's ID is the SHA-256 of its content, so management also records when an upload from the policy's server first reported each one, by management's own clock. That time bounds when the snapshot's content existed, whatever the server claims. Management keeps a receipt while the policy's reports go on listing its snapshot as available, including through a restore that verified it after the upload left the agent's run history. A snapshot pruned or left out of a report loses its receipt, and one reported again later gets a later time, so a server can make a snapshot look newer than it is but never older. A failed run records nothing, and neither does a restore of a snapshot no upload reported, which stays on the manual route. Owners and members read receipts through the policy's `receipts` endpoint.

Revoking a server records when the revocation began, and the servers list shows it as `revokedAt`. Revoking it again keeps the first time, and renewing or transferring it clears the time. A revocation from before this release has no time. A revoked server's reports are refused, so its receipts stay as they were when it was revoked.

Workspace exports and cross-host recovery carry both. Recovery keeps a receipt for each snapshot the newer of the two copies' reports lists as available, at the earlier time of the copies that have one. Of two copies of a revocation it keeps the earlier time, and when one copy has no time, it shows the time as unknown.

## Restoring a lost server's snapshot

Once a policy's server is revoked and the environment has [moved to a new primary](cross-host-placement.md#a-revoked-primary), an owner with recent authentication can restore one of the policy's snapshots onto the new primary through the policy's `recoveries` endpoint. Only a snapshot with a receipt can be chosen, and only from an S3 destination, since a filesystem repository was on the lost server. The new primary's deployment must still declare the policy's volume, or its database with the same database name and owner, and its agent must advertise `recoveryRestore`. The owner must acknowledge that a server compromised before it was revoked could have uploaded altered data, which the restore's checks can't tell from genuine data.

The policy stays bound to the revoked server and is never changed. Each restore is recorded against it, with the server it ran on, the plan applied there when it was issued and the snapshot's receipt time, and only that server is given the policy's repository access, for that restore alone. A succeeded restore's record holds the manifest the restored data matched. The data lands in a new volume, which nothing uses until a cutover.

Starting a restore needs the server's agent to advertise `recoveryRestore` as ready. Its access is released only while the restore can still go ahead: the policy is the version the restore was issued against and the policy's server is still revoked, and, the first time, the server's agent still runs the restore kind. An agent whose restore prerequisites fail at a later heartbeat still receives it, and reports the failure itself. A restore no agent has received yet ends, with a note saying why, if it is cancelled or passes its deadline, if the policy changes or its server is renewed, or if the agent no longer runs the kind. One an agent may hold is told to stop, without the access, when it is cancelled, the policy changes or its server is renewed; past its deadline, the agent ends it unless it has started it, and one that has lost it is told to stop. None of these holds up or reorders the server's other work. Workspace exports carry each policy's newest 100 restores, as the dashboard lists them, and any restore whose operation they carry.

An owner with recent authentication switches a succeeded restore's volume in through its `cutover` endpoint, which writes a draft as **Prepare cutover draft** does below. The restore's recorded result is checked again, and the environment must still run the plan the restore ran against, on the server it ran on. An environment across servers is refused as `deployment.distributed` for now. An ended restore's volume, succeeded or not, is deleted through its `target` endpoint unless the draft or the plan the server runs mounts it; the record then shows `targetDeleted`, and that volume can't be switched in.

On the dashboard, a policy whose server is revoked shows when the revocation began and no longer offers its own backup, restore or schedule controls. Owners choose a snapshot from those with a receipt, newest first and with none chosen for them. Each shows its receipt time and how long before the revocation that was, with the time the server claimed and the manifest's size, method and image marked as the server's own unverified account. The acknowledgement must be ticked for every restore. The policy's run history is labelled as the revoked server's own report, including whether a restore was verified, and its last snapshot isn't shown. The policy's restores are listed below, refreshed while any is unfinished, with **Prepare cutover draft** for a succeeded one and **Discard restored volume**, behind a confirmation, for any that has ended. A discarded volume's restore offers neither until the server reports the deletion.

## Restore and cutover

Choose an uploaded snapshot and request a fresh restore. The agent checks source ownership, repository identity, manifest checksums and capacity before creating a new volume, and downloads only the snapshot's manifest and archive. Capacity must cover the existing workload, staging and the new target; an unknown or insufficient capacity blocks restoration. PostgreSQL restore is isolated from application networks. A successful recipe check records a separate verified result and target volume.

A PostgreSQL dump's SQL runs as the cluster's superuser, and a dump from a compromised server can use that to change the cluster itself. Every restore, a lost server's included, checks the cluster before it reports success. These checks are best-effort:

- Its files, from a container that runs nothing from the volume, must be only what the pinned image's cluster holds: no links, no special files and nothing outside the data directory. The four settings files are then put back as the image wrote them, before the dump ran, and the relation cache files are removed. This runs once the dump's server has stopped, and again after the check below.
- A fresh server, with autovacuum and event triggers off, then reads the catalogs from disk. It refuses roles, passwords or memberships that differ from the cluster's before the dump ran, other databases, enabled subscriptions, settings outside the database, and setting names the server doesn't know that have no dot in them. A dump of one database holds none of these.
- Once the restored data matches the archive, settings in the database, its own or one of its roles', that only an administrator may choose are cleared: `session_preload_libraries` or `log_statement`, for example. The restore's note names each one. While the deployment's database user is a superuser, it can set again any that are still needed.

A refused restore fails with the reason, and nothing uses its volume. A superuser can rewrite the catalogs these checks read, and code in the database, such as triggers, runs as the deployment's superuser once deployed. So the checks don't make a dump from a compromised server safe to use. That needs a deployment database user that isn't a superuser, with dumps restored as that user (PLAT-450).

Choose **Prepare cutover draft**, inspect the storage change, prepare a deployment plan and explicitly apply it. Writes made to the old source after the backup are not included in the restored data. The old volume stays retained. For Compose, the draft renames an explicit volume and its mounts while preserving other source bytes; ambiguous source constructs require an explicit file edit instead of an automatic rewrite. Review the resulting source before deployment.

A PostgreSQL cutover is refused as `restore.compatibility` unless the draft's database service runs exactly the image that wrote the restored archive, with the data directory where that image keeps it. Use a supported upgrade to change major. Preparing the cutover records the target volume, with the archive's PostgreSQL major, among the environment's volumes, so it is listed there and can be deleted like any unused volume if the cutover is abandoned.

Multiple independent resource backups do not represent an application-wide transaction. No generic major-version database migration or in-place restore is included.

## Recovery without the management database

Restic's repository and encrypted snapshot contain the manifest, roles and dump/archive. Recovery requires the storage credentials, repository password, snapshot ID and ordinary Docker/PostgreSQL tools; it does not require an Astilba API or management database.

1. Install restic 0.19.1 and set `RESTIC_REPOSITORY` to the policy repository. Set `RESTIC_PASSWORD_FILE` to a private password file; supply S3 credentials through a protected environment where applicable. Keep credentials out of command arguments and shell history.
2. List snapshots with `restic snapshots --json`, select the required snapshot and run `restic restore SNAPSHOT_ID --target /srv/recovery --verify` into an empty recovery directory.
3. Locate `manifest.json` beneath the restored directory. It identifies the recipe, source image, database/user, roles, extensions and the archive's SHA-256 and byte count. Verify `data.dump` or `files.tar` against that manifest before using it.
4. For PostgreSQL, create an empty named volume and a new container using the manifest's pinned image and database/user. Supply its new password through a private Docker environment file and keep it off application networks. Wait for `docker exec recovery-db pg_isready -h 127.0.0.1 -U USER -d DATABASE`; TCP readiness excludes the temporary initialization server. Create the listed NOLOGIN roles using quoted PostgreSQL identifiers. Choose `postgres` as the maintenance database, or `template1` when restoring a database named `postgres`, then pipe `data.dump` into `docker exec -i recovery-db pg_restore --exit-on-error --clean --if-exists --create -U USER -d MAINTENANCE_DATABASE`. This recreates the archived database inside the fresh cluster. Check the restored records, schema, database settings, ownership, grants, extensions and sequences through your application's queries before reconnecting any writers.
5. For files, create an empty named volume and extract `files.tar` into it with a temporary container. Verify its content and metadata against the archive, then deliberately attach the recovered volume to a stopped application. Preserve the old volume until its retention decision is explicit.

The native fixture exercises PostgreSQL records, schema, roles, grants, identity sequences and `hstore`; it also exercises filesystem and S3-compatible repositories, quiesced file recovery and offline container jobs. These are the supported recipe checks, not evidence that arbitrary database applications or extensions are supported.

## Verification

`make check-app` covers static checks and focused scheduling/retention tests. `make verify-app` runs the real API/PostgreSQL and Chromium/WebKit journeys. `make verify-agent-host` adds the native backup/restore and offline execution fixtures on both supported architectures in CI. Prepare only an owned disposable host; install the pinned restic tool and pull this additional fixture image:

```text
dxflrs/garage:v2.4.1@sha256:9c96caa2612d3411acc5b0e6701fb238dbfba33e533a6d7d3d811a4b12d0d020
```

Garage is a test-only S3 service. The fixture uses generated credentials, loopback exposure and a private test CA; it does not weaken production HTTPS validation. See [Garage's single-node setup](https://garagehq.deuxfleurs.fr/documentation/quick-start/).
