# Backups, scheduled jobs and fresh restores

The deployment agent sends encrypted backup data directly to a workspace destination. The management database stores policies and bounded run history, not customer database dumps. A completed upload is **unverified** until a fresh restore passes its recipe checks. Preparing cutover creates a draft revision; the existing deployment-plan review is still required before traffic or storage changes.

## Supported recipes

| Source | Consistency and verification | Limits |
| --- | --- | --- |
| Managed PostgreSQL 17 or 18 | Native custom-format logical dump; restore roles and recreate the database in a new volume, in the database's own release; compare canonical SQL/data and database metadata from a second dump | Any [PostgreSQL release](supported-upgrades.md#postgresql-releases) Astilba has pinned, restored within its major; their version-specific layouts; one managed database; `plpgsql` and `hstore`; additional roles must be unprivileged NOLOGIN roles without memberships or cluster-wide role settings |
| Named file volume | Stop every declared container using the volume, reject unknown users, archive stable files, resume writers; extract into a new volume and compare its archive | Local Docker volumes with regular files, directories and symbolic links (up to 100,000 entries); all writers must be visible to this Docker daemon. Hard links and special files require another recipe. Directory timestamps are excluded from restore comparison. Do not use this recipe to claim a live database copy is consistent |
| Scheduled container job | Run an explicit argument array using an applied image worker's environment and mounts, on exactly the worker's networks without its network aliases; record its exit code | Visual image workers; never a privileged or added-capability service or one that shares a named volume or network with such a service; fixed resource bounds; missed runs are skipped; arbitrary job replay is never automatic |

PostgreSQL uses [the pinned deployment images](../services/platform/internal/domain/postgres.go). The agent dumps a database from a helper container labelled with the run, made from the database's own pinned image so its `pg_dump` matches the server. The helper shares the database container's network namespace and connects over TCP on the loopback address, which the cluster trusts, as its superuser, so no password reaches it. Each of the agent's sessions with a managed database starts with its own role, `search_path`, quoting, encoding, read-only and loading settings, which outrank any the database's user sets, so nothing that user defines runs with the superuser's privileges. Nothing runs inside the database container itself. A database whose image is not a release Astilba has pinned, current or retired, is refused, never dumped with another image. Restic is pinned to **0.19.1**. The agent advertises backup support only when that version and the deployment prerequisites are present. Install the binary from the [official release](https://github.com/restic/restic/releases/tag/v0.19.1), verifying its checksum; the disposable test installer is [backup-tools.sh](../services/platform/host/backup-tools.sh).

The encrypted agent journal keeps the verifier PostgreSQL stores for the database user's password, never the password. The agent records it when it creates or restores the database's cluster, or, for a database from before the owner model, when a backup policy for it is installed. A restore gives the user that verifier, so fresh recovery can proceed when the source container is stopped or missing. Existing source resources are still checked for ownership.

PostgreSQL recovery includes database ownership, permissions, comments, connection limits and database-specific settings, including settings for roles within that database. Existing custom-format snapshots already contain this metadata. The restore applies it as [Restore and cutover](#restore-and-cutover) describes and includes it in its comparison with the restored dump. Restoration stays in an isolated fresh cluster; a failed restore never becomes a verified cutover target. See [PostgreSQL's restore options](https://www.postgresql.org/docs/18/app-pgrestore.html).

A restore runs in the release the database runs now, not the one that took the backup, so a backup from before a pin bump restores after it: an 18.4 backup restores into a database on 18.7. A backup from another major is refused when the restore is requested, and again by the agent, with the reason; restore it into a database of its own major, or use [the major upgrade](supported-upgrades.md). Each run records the release that filled its target, and cutover checks that the database can open that data. See [PostgreSQL releases](supported-upgrades.md#postgresql-releases) for the rules.

A policy freezes its applied deployment. After a deployment changes, refresh the policy and install its new generation before expecting further backups. A failed source check does not silently back up a different resource. A new source, destination or consistency method requires a new policy.

## Destination setup

Owners with recent account verification can create reusable destinations. Credentials and repository passwords are write-only and encrypted in the management database and the agent journal. Keep the repository password and storage credentials in independent recovery records. Losing both those records and the agent's protected state makes encrypted snapshots unrecoverable.

- **S3 compatible:** provide an HTTPS origin, existing bucket, region, access credentials and the deployment server the credentials are given to (`serverId`), and optionally a `prefix`. Allow the agent to reach that origin. Each repository uses `[<prefix>/]astilba/<workspace UUID>/<policy UUID>` within the bucket. Customer private endpoints are contacted by the deployment agent, never fetched through the management service. See [storage keys per server](#storage-keys-per-server).
- **Filesystem:** create a real, private directory on the deployment server and enable its exact path with `--backup-roots`. The agent creates `<workspace UUID>/<policy UUID>/repository` and a separate ownership marker. Symlinked roots are rejected. This destination shares the server's failure boundary unless the operator provides independently durable mounted storage.

For the systemd installation, use a drop-in appropriate to the selected paths, for example:

```ini
[Service]
ExecStart=
ExecStart=/usr/local/bin/astilba-agent run --restic-cli /opt/astilba-platform-tools/restic --backup-roots /srv/backups
ReadWritePaths=/srv/backups
```

The root must already exist with suitable permissions. The agent's existing state directory remains private. A destination check opens the repository and validates its identity; installing a new policy initializes its separate encrypted repository. No shared repository pruning is used.

### Storage keys per server

restic needs to delete objects for its locks and for pruning, so every server that backs up to an S3 destination holds keys that can delete. An S3 destination therefore belongs to one deployment server, chosen when it's created, and only that server is given its keys. Give each server its own destination, with keys that can reach only that destination's prefix or bucket, so a compromised server can't delete or overwrite another server's backups. Astilba can't tell what a key can reach, so this scoping is yours to set up at the provider:

| Provider | Limit a key to |
|---|---|
| AWS S3 | A prefix: an IAM user whose policy allows object actions on `arn:aws:s3:::<bucket>/<prefix>/*` and `s3:ListBucket` on the bucket with the condition `"StringLike": {"s3:prefix": ["<prefix>/*"]}`. |
| MinIO | A prefix: an access key created with an inline `--policy` like the AWS one. |
| Backblaze B2 | A prefix: an application key created with `bucketIds` and `namePrefix` set to `<prefix>/`, with the slash, since B2 matches the start of a name and `servers/edge-1` alone would also reach `servers/edge-10`; use `astilba/` for a destination without a prefix. Give it `listFiles`, `readFiles` and `writeFiles`. restic deletes by name, which B2 records as hiding the file, so withhold `deleteFiles`, which deletes versions for good. |
| Wasabi | A prefix: an IAM sub-user with a policy like the AWS one. |
| Scaleway | A prefix: a bucket policy for the key's application, on `<bucket>/<prefix>/*`, with `s3:prefix` on listing. |
| Cloudflare R2, Garage | A bucket: these scope long-lived keys to buckets, not prefixes, so give each server its own bucket and a key for it alone. |
| Hetzner | A bucket: a key reaches every bucket in its project, so give each server its own bucket with a bucket policy that allows only that server's key, or its own project. |

A prefix is one or more path segments, separated by `/`, such as `servers/edge-1`, and at most 256 characters. Each segment starts with a letter or digit and holds only letters, digits, `.`, `_` and `-`. A destination without a prefix keeps its repositories under `astilba/`, where they always were, so limit its keys to `<bucket>/astilba/*` or give it a bucket of its own; a prefix can't begin with `astilba`. Two destinations can't share part of a bucket: a destination whose prefix equals, contains or is inside another destination's in a bucket of the same name, or that is a second destination without a prefix there, is refused with `fields: ["prefix"]`, since keys limited to one would reach the other's backups. Endpoints aren't compared, since one bucket can have several, such as AWS's regional and global origins; give same-named buckets at two providers different prefixes. Use the provider's endpoint, not one with the bucket in its host such as `<bucket>.s3.<region>.amazonaws.com`. restic puts the bucket in the host only at the AWS, Google and Aliyun endpoints it recognises, and at the start of the path anywhere else, so at a host that names a bucket the destination's own bucket becomes the start of the path within the bucket the host names. Astilba can't contact an endpoint to tell a provider's host from a bucket's, so it counts each run of an endpoint host's leading labels that is a bucket name, the whole host included, as a bucket the destination's repositories could be in, under its own bucket. A destination whose host would put its repositories in or around another's that way is refused with `fields: ["endpoint"]`, even when the host turns out to be the provider's own, and one whose part another destination's host reaches that way with `fields: ["prefix"]`. A new destination's endpoint must start with `https://` in lowercase and have a host of ASCII letters, digits, `.`, `-` and `_`, or an IP address, since other characters can be mapped onto a bucket's name. An AWS access point reaches a bucket its name doesn't say, so a new destination is refused with `fields: ["endpoint"]` for a host with an access point's alias, a label ending in `-s3alias` or `--ol-s3`, or an access point's label, `accesspoint` or one starting with `s3-accesspoint`, `s3-object-lambda` or `s3-outposts`, at any domain; and with `fields: ["bucket"]` for an alias as its bucket. Destinations created before these rules keep running. A proxy or CDN that sends requests on to a bucket of another name can't be detected, so don't put one in front of the storage. Astilba checks this within a workspace only; don't share a bucket's prefixes between workspaces. A server's agent must advertise `backupPrefixes` before a destination with a prefix can be created for it, used by its policies or restored onto it; older agents look for repositories at the bucket's root, and an agent rolled back to one keeps a prefixed schedule, with its runs, but finds it disabled and doesn't run it. If it changed the schedule's state, for example by settling a run, the schedule stays disabled once the server runs an agent that advertises `backupPrefixes` again: save the policy and install the new generation to resume it. A destination refused for its server, because the server is missing, revoked, a build server or not ready to deploy, names `serverId`.

A policy can only use an S3 destination bound to its own server, and never changes destination. Creating one on another server's destination is refused with `fields: ["destination.server"]`, and the dashboard doesn't offer such destinations. Two policies created at once can't both bind a destination: the second sees the first's server. The API lists each destination's `serverId`.

Destinations from before servers were bound were bound once, by the policies using them: to their one server, or, when policies on several servers used one, `shared`. A shared destination's keys are already on each of those servers, so its policies keep using it, but no new policy can (`fields: ["destination.shared"]`). To replace a shared destination, add one per server, create new policies on them, and then remove the old policies. A destination no policy used is bound by its first policy. Workspace imports of older archives bind destinations the same way.

Scoped keys still let a compromised server delete its own backups. To keep deleted data recoverable, enable bucket versioning and give the keys no right to delete object versions (`s3:DeleteObjectVersion` on AWS, `deleteFiles` withheld on B2 where it can be), with a lifecycle rule that expires noncurrent versions after your recovery window. Object Lock in governance or compliance mode does the same with a retention period. Each lock refresh and prune leaves a retained version, so expect some extra storage.

An S3 destination is exposed while a revoked server holds its storage keys: the server a policy using it is bound to, or one a restore of such a policy was recorded for. That server can still delete or overwrite whatever the keys reach until they are revoked at the provider. A filesystem destination has no keys, and a container job is never given any. Destinations report it as `exposed`, with the policies using each. The dashboard warns on every policy on an exposed destination. Since a new policy can only use its own server's destination, and a revoked server takes no new policies, choosing an exposed destination happens only when its own server was renewed and a server a restore ran on is the one revoked; creating a policy on one then needs `exposureAcknowledged`, which is audited as `backup.destination.exposure.acknowledge`, and one [`backup_exposure` alert](operational-alerts.md#detection-and-recovery) fires for the destination. Destinations can't be edited, so a destination stays exposed until each of those servers is renewed, even once its keys are revoked, except a [managed](#managed-keys) one, whose exposure ends an hour after AWS confirms its keys revoked, if the server isn't renewed first. Add a destination with new keys for backups a revoked server can't reach. A destination's keys stay with its own server, so the new primary of a lost server's environment needs a destination of its own for its new policies.

### Managed keys

On AWS, management can mint each server's key itself and revoke it when the server is revoked, so no server's key outlives it and none is copied by hand. Add a **storage account** once per AWS account: an IAM user's access key that can manage only the users under the workspace's path, `/astilba/<workspace UUID>/`, and the ARN of a permissions boundary every user it makes must carry. Then create a destination with `accountId` set, an empty `endpoint`, the bucket, the region and its server. Management derives the endpoint, `https://s3.<region>.amazonaws.com`, and calls only AWS's own IAM, STS and S3 endpoints, never one it is given. The prefix and bucket rules for [storage keys per server](#storage-keys-per-server) apply to it as to any S3 destination. Only the commercial `aws` partition is supported; China and GovCloud regions aren't.

Create the boundary policy first. It allows backups in the buckets you name and denies everything to temporary credentials, since any IAM user can turn its key into a session that outlives the key:

```json
{"Version": "2012-10-17", "Statement": [
  {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject", "s3:AbortMultipartUpload"], "Resource": "arn:aws:s3:::<bucket>/*"},
  {"Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::<bucket>"},
  {"Effect": "Deny", "Action": "*", "Resource": "*", "Condition": {"Null": {"aws:TokenIssueTime": "false"}}}]}
```

Then give an IAM user outside `/astilba/` this policy, and create its access key for the storage account. It can make only bounded users, under one workspace's path, and can't change or remove a boundary, so a leaked admin key can reach no more than the boundary allows. Two workspaces sharing an AWS account need an admin user each.

```json
{"Version": "2012-10-17", "Statement": [
  {"Effect": "Allow", "Action": ["iam:CreateUser", "iam:PutUserPolicy", "iam:DeleteUserPolicy"], "Resource": "arn:aws:iam::<account>:user/astilba/<workspace UUID>/*",
   "Condition": {"StringEquals": {"iam:PermissionsBoundary": "<boundary ARN>"}}},
  {"Effect": "Allow", "Action": ["iam:TagUser", "iam:GetUser", "iam:ListUserTags", "iam:ListUsers", "iam:CreateAccessKey", "iam:DeleteAccessKey", "iam:ListAccessKeys", "iam:DeleteUser"], "Resource": "arn:aws:iam::<account>:user/astilba/<workspace UUID>/*"}]}
```

Adding or replacing a storage account needs recent verification (`backup.account.create`, `backup.account.rotate`). Management checks the key first: it must belong to an IAM user, not the root user or a role; the boundary must be a policy in the same account; and it must be able to list the workspace's path, which proves the policy is attached. A replacement must come from the same AWS account, and keeps the account's boundary, since every key minted under the account carries it and the admin policy can change only users with the boundary it names; for another boundary, add another storage account. Keys already minted keep working: delete the old admin key afterwards. The admin key is sealed like any destination key and is never shown again.

Each key is an IAM user named `astilba-<key UUID>`, with the boundary, tags naming the installation, workspace, server and key, and an inline policy that allows object actions only under `[<prefix>/]astilba/<workspace UUID>/` and listing only with that prefix, and denies temporary credentials. Access is granted by the user's own policy, never a bucket policy. Creating the destination makes the user and its key, then lists the bucket inside that scope until the key works, which takes a few seconds while IAM propagates it; a key that doesn't work within five minutes, or a step AWS refuses, fails the create with an error naming it, and management revokes whatever AWS made. A restore of a lost server's snapshot from a managed destination mints its own key for the new primary, limited to that policy's repository, and revokes it within a minute of the restore ending, however it ends.

Revoking a server revokes its keys at AWS: management replaces the user's policy with one denying everything, deletes its access keys and policy, then the user, retrying with backoff up to 15 minutes until AWS confirms. The destination is [exposed](#storage-keys-per-server) until then, and for an hour after, since AWS says policy changes take a few minutes to apply, or until the server is renewed. A key revoked from a server that isn't revoked, such as a restore's own key once the restore ends, exposes nothing. The Workspace page's **Backup storage accounts** section shows the state of each key in use and of the 20 most recently revoked, and a key whose revocation keeps failing names the failure; fix it, for example by replacing a detached admin policy, and retry. Renewing the server mints a new key and installs each of the destination's policies at a new generation carrying it; the old key was revoked with the server. An install that ends without the server reporting it, for example because the agent was offline, is tried again, backing off to an hour.

Once a day, or when the owner asks, management lists the users under the workspace's path and compares them with the keys it holds. It deletes any second access key on a user it made, and reports, raising [`backup_account`](operational-alerts.md#detection-and-recovery), any user it didn't make: one restored from an older management backup, one another installation made, or one made with a leaked admin key. A user tagged with this installation and a server it has revoked is revoked without asking. A user tagged with a **peer** installation, one the account lists, is shown as that installation's; a workspace import lists the exporting installation, and the source's owner adds the importer from the alert its users raise. A peer's ID can be read from the tags of the users it made, so someone holding a leaked admin key can make a bounded user with that tag, and the peer itself may no longer check the account. So each peer's user raises its own [`backup_peer_user`](operational-alerts.md#detection-and-recovery) alert the first time a check finds it, and keeps it until the owner acknowledges that user by name (`backup.key.acknowledge`, audited, with recent verification). Acknowledge only a user that installation made. The acknowledgement covers the user as the owner reviewed it, its IAM user ID and the access keys it had, so a user made again under the same name, or given another access key, raises the alert again; one refused because the latest check found something else is reviewed again. A user without the boundary can't be acknowledged, since it isn't confined to backups, and a tag must be the peer's ID in its usual lower-case form. Acknowledgements are this installation's own, so exports leave them out, and a check that lists every user forgets those of users it no longer finds. Any other user can be revoked from the alert; a peer's user is that installation's to revoke, since a transferred server may still use its key, and the account's peers count as soon as they are added, before the next check. A user being revoked is shown as revoking, with why its last attempt failed, and one whose revocation keeps failing raises the alert. AWS won't delete a user while something else is attached to it, such as a console password, an MFA device, a group or another policy: management deletes its access keys and leaves it a deny-all policy, and the owner removes the rest in the AWS console. If AWS refuses the deny-all, for example because the user's inline policies are already at their size limit, management still deletes its access keys, which leaves it unable to act, and keeps retrying. A user without the boundary is always reported, and can't be revoked by management, since the admin policy can't change it: delete it in the AWS console. A key management holds whose user AWS no longer has is revoked and, for a server, replaced. IAM may answer a call naming a user that doesn't exist with AccessDenied rather than NoSuchEntity, since it can check the call against the user's ARN without its path, which the admin policy's path-scoped resources don't match. Management treats either answer as the user being gone, but takes AccessDenied as gone only when the user also isn't listed under the workspace's path, and then only with more: for a key whose secret it holds, that AWS no longer accepts the key itself; for a found user, nothing more, since the check already listed it under the path; for a mint that never finished, that the key's row is old enough that the mint would have finished and the listing caught up, and until then the revocation shows `not_listed` and retries. A user someone with wider IAM rights moved off the path answers the same way, and keeps its keys: its key stays revoking with `moved_off_path`, and like any key management holds whose revocation keeps failing, it raises [`backup_account`](operational-alerts.md#detection-and-recovery) after three attempts, until the owner deletes the user in the AWS console or moves it back. The admin key can't move users. Which of the two answers IAM actually returns hasn't been confirmed against AWS yet; the code is correct either way.

To transfer a workspace, revoke its source servers with **hand over storage keys** (`handOverStorageKeys`, audited as `backup.key.handover`), so their installed schedules keep working; see [transfer a workspace](hosting.md#transfer-a-workspace-between-installations). A handed-over key isn't exposed and is shown as handed over. Revoking it at the source afterwards breaks the transferred server's backups. The handover is bound to that revocation: renewing and revoking the server again revokes the key unless it is handed over again. Exports carry storage accounts, with their admin keys, and the keys management minted. Each installation acknowledges the other's users once each: the source each user the importer makes after it is added as a peer, such as the keys it mints when it renews the transferred servers, and the importer each user the source made after the export.

Managed keys are AWS-only. Other providers' minting credentials can't be confined the way an IAM boundary confines one, so their keys stay yours to scope as above.

## Scheduling, retention and interruptions

Choose daily, cron or fixed-interval schedules. An existing daily policy keeps its original schedule representation and digest, including an empty timezone interpreted as UTC.

| Schedule | Timing |
| --- | --- |
| Daily | A local hour/minute in an IANA timezone, such as `Europe/London`. |
| Cron | Five fields: minute, hour, day of month, month, weekday. Supports lists, ranges, steps and month/weekday names; weekdays are 0–6 (Sunday–Saturday). `0 2 * * MON-FRI` runs at 02:00 on weekdays. Restricted day-of-month and weekday fields use OR semantics. No seconds, `@` shortcuts or embedded timezone prefixes. |
| Fixed interval | 1–525600 elapsed minutes, anchored to the first installed UTC instant. The first run is one interval after installation; later runs do not drift with job duration or daylight-saving changes. A new installed generation resets the anchor. |

Daily/cron schedules skip nonexistent local times and choose the first occurrence of a repeated wall-clock minute, including half-hour transitions. Cron expressions require an explicit IANA timezone; interval schedules use UTC. Calendar lookup uses the pinned parser's five-year look-ahead; an unavailable next occurrence blocks installation or execution instead of spinning or guessing.

The dashboard formats next runs in the configured timezone. If that zone is unavailable in the browser, it labels a UTC display without changing the schedule.

A job's command could drive a privileged service that its source shares a named volume or a network with, so management refuses to save or run a job whose source deployment review treats as elevated, and the agent refuses it again before each run, also checking the containers the daemon runs beside the source. The job container joins the same networks as the source container, each of which must belong to the deployment, or none if the source has none.

Each run's identity includes policy ID, generation and scheduled UTC instant. The agent persists the next instant together with its run record before host effects. Restart, reconnect and backward clock changes cannot replay an admitted run. Forward clock changes follow the missed-run rules: missed backups coalesce into one catch-up for the latest due instant, while container jobs more than one minute late are skipped with a history record. There is no arbitrary job replay or configurable parallelism.

Jobs and backups share the host execution lock with deployments and upgrades. If the host is busy, the same catch-up/skip rules apply when it becomes available. Installed schedules continue while management is unavailable; bounded reports upload when it returns. Disabling a local schedule requires delivery to that agent. Installing or disabling a schedule commits it together with its command's outcome, checking a repository changes nothing, and each step of creating a repository can be repeated, so an agent stopped during one of these runs it again rather than holding the host's schedules for inspection. One run again after its deadline ends cancelled with no schedule changed, except an install that had begun creating its repository, which may run again until its lifetime after the agent first started it. If the agent stopped while writing a new repository's ownership marker, the install fails as a mismatch rather than adopt the directory.

Upload/job timeouts can be set from 1 to 1800 seconds; omission preserves the thirty-minute limit. Restores retain their separate thirty-minute limit. A backup or restore command's lifetime is its run's limit plus ten minutes, and never less than thirty minutes. It may start until that long after management issues it, its deadline, and once the agent starts it, after any wait behind other work on the host, it may run for that long. So a run that runs long ends by its own limit rather than by its command's bound, and a run-now backup queued behind a long scheduled run still gets its whole lifetime. A command that reaches the host after its deadline, for example because its agent was offline, never starts, whatever the host's clock reads, and management no longer sends its repository access. A timed-out job stops and removes only its owned run container, with up to thirty additional seconds to confirm cleanup and record the exit result. A timeout is never evidence of successful application work.

General schedules and custom timeouts require an updated agent advertising the negotiated `schedules` capability. Extended commands use the `schedule` kind, which older executors reject before effects. Current agents omit this capability when talking to older management schemas. The management database advances to schema 17 and older management binaries refuse startup against it.

Advanced schedules remain encrypted in a versioned agent journal bucket, alongside a disabled legacy mirror of their run/writer fences. A rolled-back agent cannot run their cadence, but can still recover recorded writers and block operations over unresolved runs. After an older agent changes or resolves that state, the newer agent honors its newer generation/sequence rather than resurrecting hidden advanced work. The dashboard shows the effective disabled state; save and install a new policy generation to resume general scheduling. Controller transfer preserves policy IDs, history and interval cursors and still refuses unresolved effects.

Retention considers only this policy's catalogued snapshots after a successful upload. It keeps the configured recent uploads, the newest demonstrated recovery point and the snapshot of any restore that is running or unresolved. A restore that ends, whether it succeeds, fails or is resolved, releases its snapshot. Unknown snapshots are left alone. Maintenance has a bounded repack size and operation deadline. Restores have a thirty-minute execution limit; upload/job limits are described above. Full manifests stay in the encrypted repository; operational records carry their hash and compact metadata. History is bounded to 128 records per policy while retaining a representative of each available snapshot; redundant completed restore records can age out. History keeps the run that uploaded each available snapshot rather than a restore of it. Unresolved protected history can require operator attention instead of being silently discarded.

An interrupted run does not become a success. A run stopped before its first effect fails. One that fails or is stopped after it began changing things, by a cancel, its command's bound, its own limit or the agent stopping, fails only once its cleanup is confirmed: every container labelled with the run (its dump or data helper, restore database or job) is removed, which ends whatever ran in it (a database connection it held ends within a second), and restic has exited. Otherwise the run and its command need attention, and the run's note names what could not be confirmed, such as a container Docker would not remove. So does a run the agent was killed or crashed during, which nothing could clean up. A run that fails leaves no usable record: a snapshot restic uploaded before the run stopped stays uncatalogued, and a restore's target volume is retained. Inspect any containers with the run's `com.astilba.run` label and the retained target volume. Once uncertain containers are stopped and the outcome is understood, a local operator can close the failed run:

```sh
astilba-agent resolve-run --policy POLICY_UUID --run RUN_UUID
```

This resumes recorded file writers where their identity still matches, refuses active run containers, and records failure rather than claiming a valid backup. It also records the run's own command as failed. Any other operation the host refused while the run was unresolved still needs `astilba-agent retry`. The operator can then retry a new run. A restore's snapshot stays protected until its run is resolved. A run under a coordinated reservation is resolved with `astilba-agent reject-cross-host-effect` instead; see [Cross-host placement](cross-host-placement.md). Existing application data is never deleted by these operations.

A backup or restore writes the repository's password to a file the restic process reads, and stages data on its way to or from the repository, all in the agent's state directory. The agent removes each when its command step ends. One killed or crashed part way leaves them behind: they hold the password, a dump of the data, or a partial download that counts against the space the next restore needs. When the agent opens its journal again, before it takes any command, it removes them. It matches only the names it gives them (`restic-access-`, `backup-stage-`, `restore-stage-`, `restore-verification-`, `upgrade-stage-` and `upgrade-download-` followed by digits), as the kind of entry it makes, and logs their names. It leaves an entry with such a name that it did not make, and logs that too. Containers and target volumes an interrupted run left are resolved as above.

A restore of a lost server's snapshot onto its replacement uses the `restore` command kind, which only an agent advertising `recoveryRestore` receives: an older agent would hold the command unsettled. The replacement holds no schedule for the lost server's policy. It reads only the manifest and the archive file beside it out of the snapshot, and no more of the archive than the manifest gives as its size. Before creating anything it refuses a snapshot not written for the policy's environment, resource and method, one holding other than exactly one manifest with an archive file beside it, an archive that differs from its manifest, a database archive made with an image Astilba doesn't pin or for another database or owner than the deployment's, or a target volume the deployment declares. The database user's password is the replacement's own database's, as the verifier the agent recorded for it. The restore's own container has no network, can't gain privileges and mounts only its target volume. A database restore runs as `postgres` with no capabilities, and a file restore keeps only those that restoring owners and modes needs. The archive reaches it only through standard input. A restore stopped after it began creating its target fails once nothing labelled with its run is still running. Otherwise it needs attention, without the repository's access, until `resolve-run` with the lost server's policy and the run settles it.

## Snapshot receipts

A server reports its own times for the snapshots it uploads, and a host that was compromised can backdate them. A snapshot's ID is the SHA-256 of its content, so management also records when an upload from the policy's server first reported each one, by management's own clock. That time bounds when the snapshot's content existed, whatever the server claims. Management keeps a receipt while the policy's reports go on listing its snapshot as available, including through a restore that verified it after the upload left the agent's run history. A snapshot pruned or left out of a report loses its receipt, and one reported again later gets a later time, so a server can make a snapshot look newer than it is but never older. A failed run records nothing, and neither does a restore of a snapshot no upload reported, which stays on the manual route. Owners and members read receipts through the policy's `receipts` endpoint.

Revoking a server records when the revocation began, and the servers list shows it as `revokedAt`. Revoking it again keeps the first time, and renewing or transferring it clears the time. A revocation from before this release has no time. A revoked server's reports are refused, so its receipts stay as they were when it was revoked.

Workspace exports and cross-host recovery carry both. Recovery keeps a receipt for each snapshot the newer of the two copies' reports lists as available, at the earlier time of the copies that have one. Of two copies of a revocation it keeps the earlier time, and when one copy has no time, it shows the time as unknown.

## Restoring a lost server's snapshot

Once a policy's server is revoked and the environment has [moved to a new primary](cross-host-placement.md#a-revoked-primary), an owner with recent authentication can restore one of the policy's snapshots onto the new primary through the policy's `recoveries` endpoint. Only a snapshot with a receipt can be chosen, and only from an S3 destination, since a filesystem repository was on the lost server. The new primary's deployment must still declare the policy's volume, or its database with the same database name and owner, and its agent must advertise `recoveryRestore`, and `backupPrefixes` too for a destination with a prefix. The owner must acknowledge that a server compromised before it was revoked could have uploaded altered data, which the restore's checks can't tell from genuine data.

The policy stays bound to the revoked server and is never changed. Each restore is recorded against it, with the server it ran on, the plan applied there when it was issued and the snapshot's receipt time, and only that server is given the policy's repository access, for that restore alone. A succeeded restore's record holds the manifest the restored data matched. The data lands in a new volume, which nothing uses until a cutover.

A restore gives the new primary the lost server's destination keys for as long as it runs, and the new primary's agent could keep them, so the destination is exposed if the new primary is revoked too. Rotate those keys at the provider once the restore has ended if that matters to you. The new primary's own policies need a destination of their own.

Starting a restore needs the server's agent to advertise `recoveryRestore` as ready. Its access is released only while the restore can still go ahead: the policy is the version the restore was issued against and the policy's server is still revoked, and, the first time, the server's agent still runs the restore kind. An agent whose restore prerequisites fail at a later heartbeat still receives it, and reports the failure itself. A restore no agent has received yet ends, with a note saying why, if it is cancelled or passes its deadline, if the policy changes or its server is renewed, or if the agent no longer runs the kind. One an agent may hold is told to stop, without the access, when it is cancelled, the policy changes or its server is renewed; past its deadline, the agent ends it unless it has started it, and one that has lost it is told to stop. None of these holds up or reorders the server's other work. Workspace exports carry each policy's newest 100 restores, as the dashboard lists them, and any restore whose operation they carry.

An owner with recent authentication switches a succeeded restore's volume in through its `cutover` endpoint, which writes a draft as **Prepare cutover draft** does below. The restore's recorded result is checked again, and the environment must still run the plan the restore ran against, on the server it ran on. An environment across servers is refused as `deployment.distributed` for now. An ended restore's volume, succeeded or not, is deleted through its `target` endpoint unless the draft or the plan the server runs mounts it. A plan prepared but not applied mounts it only if the draft still does, since a plan applies only from the draft's revision. The record shows its latest discard as `discard`. While that discard, or any other delete of the volume, is active, the volume is neither switched in nor discarded again. Once the volume is deleted the record shows `targetDeleted`, and it can't be switched in. A failed or cancelled discard leaves it usable. A cutover and a discard of one restore are decided one at a time, as any delete of a volume and a draft that uses it are (see [visual deployments](visual-deployments.md)), so they can't both succeed. A refused discard is a `conflict`, and when the reason is the restore's own, its `fields` name it with one of these stable values: `discard.active` (a discard or other delete of the volume is still running, which also refuses a cutover), `volume.deleted` (the volume is already deleted), `volume.inUse` (the draft, the plan the server runs or a supported upgrade uses it, as deleting any volume reports) and `restore.server` (the environment no longer runs on the server the restore was made on). Any other conflict, such as an inactive environment or a busy server, carries its own message. A workspace export carries each restore's latest discard. An import cancels it if it hadn't ended, as it cancels any unfinished operation.

On the dashboard, a policy whose server is revoked shows when the revocation began and no longer offers its own backup, restore or schedule controls. Owners choose a snapshot from those with a receipt, newest first and with none chosen for them. Each shows its receipt time and how long before the revocation that was, with the time the server claimed and the manifest's size, method and image marked as the server's own unverified account. The acknowledgement must be ticked for every restore. The policy's run history is labelled as the revoked server's own report, including whether a restore was verified, and its last snapshot isn't shown. The policy's restores are listed below, refreshed while any is unfinished, with **Prepare cutover draft** for a succeeded one and **Discard restored volume**, behind a confirmation, for any that has ended. While a restore's discard is active, or once its volume is deleted, the restore offers neither, after a reload too. A refused discard is explained in its confirmation, which stays open, and an accepted one is shown at once, so the restore holds its volume even if the reload fails, until the next load shows what the server recorded. Each restore's volume status announces its discard's progress and outcome, and keeps a failed discard's note.

## Restore and cutover

Choose an uploaded snapshot and request a fresh restore. The agent checks source ownership, repository identity, manifest checksums and capacity before creating a new volume, and downloads only the snapshot's manifest and archive. Capacity must cover the existing workload, staging and the new target; an unknown or insufficient capacity blocks restoration. PostgreSQL restore is isolated from application networks. A successful recipe check records a separate verified result and target volume.

Every PostgreSQL restore, a lost server's included, creates a cluster in the owner model (see [managed database roles](visual-deployments.md#managed-database-roles)), whatever model the archive's server had, and never runs the dump as a superuser:

- The superuser creates the database user, the manifest's other roles, which the user is a member of, and an empty database the user owns, with the server's own encoding and locale.
- `pg_restore` restores the dump as the database user, without `--create`. While object owners are set, the superuser lets the manifest's other roles create objects in the database and its schemas, and takes exactly that back before the dump's own grants are restored.
- The dump's statements about the database itself, its owner, comment, connection limit, template flag, settings and grants, are read from the archive and held to the forms `pg_dump` writes. Anything else refuses the restore. They run as the database user, in one session, each in its own transaction, and the first that fails stops the rest and fails the restore. Settings the user can't choose are left out, and the restore's note names each one: those only an administrator may choose, such as `session_preload_libraries` or `log_statement`, a module's custom settings, which the user's session can set only while the module is loaded, who a session runs as (`role` and `session_authorization`), which would also decide who the restore's own sessions run as, the random `seed`, those PostgreSQL only still accepts and ignores (`default_with_oids` and `ssl_renegotiation_limit`), and other roles' settings in the database.

So a dump's code, even a compromised server's, can do no more than the deployment's database user could. A dump that needs a superuser doesn't restore, such as one with event triggers, subscriptions, C functions, casts between built-in types, or functions that set a module's setting, which only a database whose user was the superuser can hold. Nor does one with privileges the user can't grant: those changed on PostgreSQL's own catalog or on an extension's objects, and those granted by a role that doesn't own the object, which a role given a grant option can make. A backup of a database holding either is refused with that reason, since no restore could use it, and a restore of an older such dump fails, and nothing uses its volume.

Once the dump's server has stopped, the restore checks the cluster before it reports success:

- Its files, from a container that runs nothing from the volume, must be only what the pinned image's cluster holds: no links, no special files and nothing outside the data directory. The four settings files are then put back as the image wrote them, and the relation cache files are removed. This runs once the dump's server has stopped, and again after the checks below.
- A fresh server, with autovacuum and event triggers off, then reads the catalogs from disk as the superuser. It refuses roles, passwords or memberships that differ from the cluster's before the dump ran, other databases, enabled subscriptions, settings outside the database and its user's, and settings the user can't choose.
- The restored data must match the archive, and so must the database's own statements, less the settings left out. A database whose encoding or locale isn't the server's is refused. How a dump prints values depends on its session's settings, which the database's user can choose, such as the time zone of timestamps and how `bytea` and `money` print. So a backup records the dump's in its manifest as `dumpSettings`, which only the snapshot holds, its dump runs with exactly those, and the restore's dump that it compares runs with them too. An agent from before `dumpSettings` can't restore such a backup locally, which is why agents now refuse to go back to one; see [minimum version](agent.md#minimum-version). For an archive from before they were recorded, which was dumped as the database user, it uses that user's settings in the restored database. Such an archive must hold its database's comment and settings as UTF-8 with standard quoting, as it does unless the database chose another `client_encoding` or turned `standard_conforming_strings` off.

The database user then gets its password, as the verifier PostgreSQL stored for it. That is the one the agent recorded for the database, as above. A refused restore fails with the reason, and nothing uses its volume. A restore's result carries `restoreRoles: "owner"`, and its cutover draft gives the database the owner model; a distributed deployment's cutover records that model in its boundary, and its agent checks it against the run. A cutover from a restore without it, such as one an earlier agent ran, is refused for a database already in the owner model. Data from a compromised server is still that server's data: the restore keeps it from reaching beyond its database, not from being wrong.

Choose **Prepare cutover draft**, inspect the storage change, prepare a deployment plan and explicitly apply it. Writes made to the old source after the backup are not included in the restored data. The old volume stays retained. For Compose, the draft renames an explicit volume and its mounts while preserving other source bytes; ambiguous source constructs require an explicit file edit instead of an automatic rewrite. Review the resulting source before deployment.

A PostgreSQL cutover is refused as `restore.compatibility` unless the draft's database service runs a release that opens the data the restoring release wrote: the same major and Alpine line, no older, mounted where that release keeps its data. Use a supported upgrade to change major. Preparing the cutover records the target volume, with the restoring release's PostgreSQL major, among the environment's volumes, so it is listed there and can be deleted like any unused volume if the cutover is abandoned.

Multiple independent resource backups do not represent an application-wide transaction. No generic major-version database migration or in-place restore is included.

## Recovery without the management database

Restic's repository and encrypted snapshot contain the manifest, roles and dump/archive. Recovery requires the storage credentials, repository password, snapshot ID and ordinary Docker/PostgreSQL tools; it does not require an Astilba API or management database.

1. Install restic 0.19.1 and set `RESTIC_REPOSITORY` to the policy repository. Set `RESTIC_PASSWORD_FILE` to a private password file; supply S3 credentials through a protected environment where applicable. Keep credentials out of command arguments and shell history.
2. List snapshots with `restic snapshots --json`, select the required snapshot and run `restic restore SNAPSHOT_ID --target /srv/recovery --verify` into an empty recovery directory.
3. Locate `manifest.json` beneath the restored directory. It identifies the recipe, source image, database/user, roles, extensions, the settings the dump ran with, and the archive's SHA-256 and byte count. Verify `data.dump` or `files.tar` against that manifest before using it.
4. For PostgreSQL, create an empty named volume and a new container using the manifest's pinned image and database/user. Supply its new password through a private Docker environment file and keep it off application networks. Wait for `docker exec recovery-db pg_isready -h 127.0.0.1 -U USER -d DATABASE`; TCP readiness excludes the temporary initialization server. Create the listed NOLOGIN roles using quoted PostgreSQL identifiers. Choose `postgres` as the maintenance database, or `template1` when restoring a database named `postgres`, then pipe `data.dump` into `docker exec -i recovery-db pg_restore --exit-on-error --clean --if-exists --create -U USER -d MAINTENANCE_DATABASE`. This recreates the archived database inside the fresh cluster. Check the restored records, schema, database settings, ownership, grants, extensions and sequences through your application's queries before reconnecting any writers.
5. For files, create an empty named volume and extract `files.tar` into it with a temporary container. Verify its content and metadata against the archive, then deliberately attach the recovered volume to a stopped application. Preserve the old volume until its retention decision is explicit.

The native fixture exercises PostgreSQL records, schema, roles, grants, identity sequences and `hstore`; it also exercises filesystem and S3-compatible repositories, quiesced file recovery and offline container jobs. These are the supported recipe checks, not evidence that arbitrary database applications or extensions are supported.
