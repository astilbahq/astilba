# First Env monorepo release

Prepare `@astilba/env` **0.3.1**, with future tag `env/v0.3.1`. It is an unreleased patch candidate for the repository/provenance handover, not a new API or runtime feature. On 14 October 2026, registry version history ends at 0.3.0; neither repository contains a 0.3.1 release tag. This observation does not reserve the version: recheck availability immediately before publication and stop if it has been used.

This PR changes source version and its exact verification baseline only. Public exports, supported runtime/consumer matrix and deterministic generated formats remain unchanged. The generator does not embed the package version, so its checked-in versioned `v1` formats and fixtures remain unchanged. Docs/apex and independent registry examples continue consuming released Env 0.3.0. UI and Cache, including private Cache #94, are excluded.

## Current controls and trust

Publishing is disabled by the absent `ENV_PUBLISHER_ENABLED` variable. Merging this PR does not authorize enabling it or creating a tag, GitHub release, npm publication, staged publication or deployment.

The configured `npm-env` environment requires manual ReesMorris approval, allows self-approval under the sole-maintainer decision, forbids administrator bypass and allows only `env/v*` tags. Separate active tag rules restrict creation to ReesMorris and prohibit updates/deletions without bypass. [Repository settings](repository-settings.md) records the control identities; recheck live settings before use.

The authenticated npm readback on 14 October 2026 returns the existing GitHub binding `astilbahq/env`, `release.yml`, environment `npm`, with `createPackage` and `createStagedPackage` permissions. Connection IDs stay in maintainer-private evidence, not this repository. The intended new Env-only binding is `astilbahq/astilba`, workflow filename `release-env.yml`, environment `npm-env`. No connection is added, replaced or revoked by this PR. Package publishing-access policy still needs authenticated settings readback; account 2FA does not prove that token publishing is disabled.

## Separately approved release window

1. Merge only the reviewed candidate after all required checks and both eligible bot reviews are clear. Recheck current main, npm version history, both repositories' tags/releases, old release activity, environment/tag protections and package-owner access. Confirm 0.3.1 is unused and retain both enable variables absent. The tag must point to verified **current** main, not merely an ancestor or this PR's pre-squash head.
2. Obtain explicit approval for trust changes, pausing the old publisher and the first real publication. An npm package owner completes any fresh 2FA step-up. Read all current connections and publishing policy; privately record old IDs and exact identities. Use npm's current package-settings interface to add the Env-only binding alongside the old one and read it back. If the installed CLI only reports one connection or refuses coexistence, stop and use the current authenticated interface; never revoke the old binding merely to satisfy that CLI.
3. Request direct publish permission, not dist-tag management, and record effective permissions. npm's current interface automatically permits staging for new connections; `allowStagePublish: false` in the preparation manifest expresses workflow intent, not proof that npm disables staging. This workflow never stages. Review any permission discrepancy before proceeding. Add trust only within the approved window: an unused new connection expires after two days. Preserve the old binding until successful acceptance.
4. Pause the old Env release workflow and verify no old release job is running, without changing its historical tags/releases or any deployment workflow. Then, and only with publication approval, enable `ENV_PUBLISHER_ENABLED`, recheck main/version availability and create immutable `env/v0.3.1` on that verified main commit. Its tag push triggers the complete Env matrix and the protected publish job. Manual environment approval is still required; recheck identity after the environment wait. Do not create a GitHub release to start Env publishing: the workflow creates it only after npm verification.
5. Verify the published npm archive matches the verified source-bound artifact bytes, clean consumer acceptance, npm signatures and both attestation types. Require the exact monorepo, `release-env.yml`, tag, commit and SHA-512 subject identity. Verify the GitHub release's archive and manifest by rereading and downloading both assets. Local rehearsals and green PR checks do not establish live OIDC/provenance acceptance.
6. After successful acceptance, separately approve revoking only obsolete Env connection IDs, verify token-based publishing is disabled, and retire the old Env publisher through its own reviewed change. Do not remove UI trust, disable deployment workflows or archive old repositories. Disable the monorepo enable variable again at the end of this first-release window unless ongoing publication authority is explicitly approved.

## Stop and recovery

Before npm accepts an archive, leave/remove the enable variable and stop tag/release creation. If a tag or release already exists, do not move, delete or recreate it to retry; use the workflow's verified idempotent path only after reviewing the failure. If npm accepts 0.3.1 but later verification or GitHub asset creation fails, disable publishing and investigate that exact immutable version. Never republish, overwrite or unpublish it as an automatic rollback, and never return the old publisher to service for the same version. Any new version or recovery publication needs fresh approval.

[npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) documents multiple immutable connections, new-connection expiry and effective publishing permissions. [The npm trust CLI](https://docs.npmjs.com/cli/v11/commands/npm-trust/) documents package write access and 2FA requirements; its legacy one-connection description must not override authenticated current registry behavior.
