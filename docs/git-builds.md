# Git and build workflows

Imports and builds run on an enrolled **Build** or **Combined** runner. The management application contacts provider APIs for repository metadata and the Git object name of each imported file, schedules frozen commands and submits saved drafts for review itself; it never clones or builds locally. A runner builds code that may be hostile, so it only ever receives a credential that can fetch: never the API credential, and never a clone credential the Git server would let push to the repository. Deployment-only servers cannot receive pipeline work. GitHub, GitLab and Gitea use the same import, submission and exact-commit build workflow. Customer runners and registries work without an Astilba-hosted account.

## Connect a repository

An owner with recent authentication creates a repository connection under **Git and builds**. Use the configured GitHub App to authorize and select a repository, or use the manual GitHub, GitLab or Gitea credential form with an exact provider origin and repository path. GitHub uses https://api.github.com internally; https://github.com is accepted at creation. Hosted GitLab and Gitea are supported directly. For other GitLab/Gitea origins, the management operator configures a comma-separated **ASTILBA_INTEGRATION_ORIGINS** allowlist. Explicit origins may reach private networks, so allow only trusted provider endpoints. HTTPS with publicly trusted certificates is required; numeric loopback HTTP is available only in local development.

A manual connection has two credentials:

- The **API credential** stays in management. It reads repository metadata and the selected files, and creates the submission branch, commit and review. Give a public repository one too rather than sharing the provider's low anonymous rate limit.
- The **clone credential** is the only one a runner receives, for private repositories. It must not be able to push. Astilba asks the Git server whether it could push to this repository over HTTPS, without pushing anything, when you create the connection and again before each runner receives it. It refuses the credential if the answer is yes or unclear, or if the server doesn't accept the credential at all. That check can't see a token's other permissions, such as managing deploy keys, adding SSH keys to its account, or writing to other repositories, so create exactly the credentials the table lists and nothing broader. A connection whose clone credential is refused can't import or build until it has a read-only one. Replacing a connection's credentials in place is planned (PLAT-147); until then, create a new connection and point the source and build targets at it.

| Provider | API credential | Clone credential |
|---|---|---|
| GitHub | Fine-grained token for only this repository: **Metadata: read**, **Contents: read and write**, **Pull requests: read and write** | Fine-grained token for only this repository: **Contents: read** (Metadata read is included) |
| GitLab | Project access token, Developer role, `api` scope | Deploy token with only `read_repository` |
| Gitea | Token with `write:repository` | Token with only `read:repository` |

Submitting drafts to Gitea needs Gitea 1.20 or later, the first release that can start a branch at an exact commit and change several files in one commit. Astilba asks the server for its version first and refuses an older one before writing anything.

Use credentials that expire, and rotate them at the provider. A Gitea token, and a GitHub classic token, reaches every repository its account can, so for those create a machine account that can read or write only this repository. A GitLab deploy token and a fine-grained GitHub token are scoped to one repository by the provider. SSH clone support is outside this milestone. Connections retain their repository identity and credentials rather than accepting a repository URL in each job. A repository ID or visibility change requires an explicit new connection; branch resolution and queued credential delivery recheck that identity. A Gitea repository counts as private unless its owner is public too, because only then can it be cloned without a credential.

The webhook URL and random secret appear once after creation. Configure **push** events in the repository, retaining the raw request body. GitHub and Gitea use HMAC-SHA256; GitLab uses its secret-token header and delivery identifier. Each delivery is checked against the connected repository ID. Delivery replay is deduplicated, retained delivery records are capped, and refresh jobs coalesce while active. A push starts a refresh only for a branch that a source imports or a target builds automatically; a push for any other branch is accepted and starts nothing. Refreshes, submissions, previews and GitHub App events run in a background queue of their own, so they never delay deployments or other background work, and each workspace's jobs there take turns with other workspaces' (see [operational bounds](hosting.md#operational-bounds-and-retention)). Refresh resolves the current authoritative branch through the provider API, so an older delivery cannot roll the source backwards. A refresh that finds the source on the branch's commit while another commit is being imported waits for that import: if you force-push a commit away while it is being imported, the source and draft then return to the branch's commit by themselves, the import of the branch's commit says in job history that the branch moved back, and an automatic deployment of the removed commit is blocked. Fork and pull-request events do not receive build credentials.

## GitHub App onboarding

The management operator registers one GitHub.com App for the installation. Workspace owners choose **Continue with GitHub**, authorize their GitHub identity and select an installation/repository. Install the App or change its selected repositories through the provided GitHub link, then refresh the list. Only a repository administrator can delegate access to a workspace. Manual credentials and GitLab/Gitea remain available.

The App acts as a workspace bot: its connection survives changes to the original administrator’s GitHub membership or OAuth authorization. Disconnect it in Astilba or remove/suspend the installation to stop future access. Disconnect and confirmed installation revocation cancel pending Git work and require renewed approval for automatic imports/builds/deployments. Reconnect only to the same repository ID, path and visibility; create a new connection after a rename, transfer or visibility change. Workspace export/import carries the connection description, but never the controller’s App authority: authorize again on the destination.

OAuth state and S256 PKCE are bound to the account, authentication version, workspace and login session for ten minutes. Confirming identity preserves that unfinished connection unless it uses a recovery code; a new login does not. Codes and temporary user tokens never enter browser storage or runner assignments. Expired proofs are removed by management’s bounded maintenance sweep. The browser binding is established at sign-in; sessions from older versions without a binding must sign in or confirm identity before starting authorization. The existing Strict session cookie remains unchanged.

The controller mints tokens for the one connected repository. Runners receive one with only **Contents: read**, for import and build checkout. Submissions use a separate one with **Contents: write** and **Pull requests: write**, which management mints and uses itself and never sends to a runner. GitHub makes every installation token last one hour, so a runner's read token can stay valid for up to an hour after the run that received it. The controller checks the permissions and repository GitHub grants each token and refuses anything broader. It reuses tokens only with at least 35 minutes remaining, with a 512-entry memory limit and coalesced requests. Successful installation and exact repository identity/visibility checks can be reused for at most five seconds; every credential delivery still checks the local active binding. A missed revocation webhook can therefore take up to five seconds to block new credentials. Already delivered credentials and already running work cannot be recalled instantly. GitHub’s own token revocation and expiry still apply.

The App webhook authenticates raw bytes with HMAC-SHA256 and deduplicates delivery IDs/body hashes. Sanitized durable events fan out in bounded pages; refresh resolves current authoritative branch state. Installation changes reconcile current GitHub authority, preventing old events from undoing a fresh authorization. Unsupported event types do not create pipeline work. This does not enable pull-request previews or fork credentials.

### Operator setup

Register a GitHub App with these settings, substituting your management origin:

- Callback URL: `https://platform.example.com/github/callback`.
- Setup URL: `https://platform.example.com/github/installed`. Leave **Request user authorization during installation** off; Astilba starts authorization with PKCE separately.
- Webhook URL: `https://platform.example.com/hooks/github-app`, with a random secret of at least 32 characters and SSL verification enabled.
- Repository permissions: **Metadata: read**, **Contents: read/write**, **Pull requests: read/write**. No administration or workflow write permission is needed.
- Subscribe to **Push**. GitHub also sends installation, installation-repository and authorization lifecycle events.

Set `ASTILBA_GITHUB_APP_ID`, `ASTILBA_GITHUB_APP_CLIENT_ID`, `ASTILBA_GITHUB_APP_SLUG`, `ASTILBA_GITHUB_APP_CLIENT_SECRET`, `ASTILBA_GITHUB_APP_WEBHOOK_SECRET`, and exactly one of `ASTILBA_GITHUB_APP_PRIVATE_KEY_FILE` or `ASTILBA_GITHUB_APP_PRIVATE_KEY`. The file must be an owner-only regular PEM file; inline PEM suits a secret manager or container environment. Use an RSA key of at least 2048 bits. Keep these values in private deployment configuration. Partial configuration prevents management startup; omitting all values keeps the manual credential path available. App registration by manifest and GitHub Enterprise are outside this increment.

All token exchange, authorization and credential hydration stay in Go.

Official GitHub references: [App security guidance](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app), [OAuth and PKCE](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), and [scoped installation tokens](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app).

## Import and submit Compose

Create a **Compose files** environment and select the connection, branch, runner, optional fallback, entrypoints and supporting paths. The runner fetches the assigned commit and imports regular UTF-8 files, preserving their contents. The existing [Compose limits and runtime rules](compose-deployments.md) apply. Reload the current revision after a completed import; unsaved editor contents are never replaced automatically.

Management does not take a runner's word for the files. When it starts an import it asks the provider for the Git object name of each selected file at that commit, one request per file on GitHub and GitLab, or one per directory on the way to each file on Gitea, whatever the repository's size. On Gitea, a listing too long to read within its limit counts as the provider not answering. When the runner reports back, any file that doesn't match fails the import with nothing saved, and the job's note says the files differ: treat that runner as compromised until you can explain it. A large-file pointer is imported and compared as its pointer text. A runner refuses symlinks and submodules, and one that doesn't can at most import a link's own stored target as text. If the provider can't read those files, whether from an outage, a rate limit or a credential without read access to contents, the import doesn't start and no runner is held. A refresh you start reports this straight away. One started by a push looks again every minute for a day, shows the commit as not yet imported on the source, and holds back only that environment's automatic builds, which build on the imported draft. The next push or a refresh you start takes over after that. A branch the provider says does not exist twice in a row, about a second apart, as after it is deleted, ends that branch's refresh, and a push that recreates it starts another. A provider that can't resolve the branch for any other reason stops the whole refresh for that branch, which retries with increasing delays and shows nothing on the source. A refresh started by a push has about 7 seconds per attempt to read files. A source too slow for that needs a refresh you start, which has longer.

Save changes, then **Submit saved draft for review**. Management makes the submission itself, through the provider's API with the connection's API credential; no runner takes part. It creates one create-only branch, `astilba/<submission id>`, for that revision, with one commit whose only parent is the imported commit, and one pull or merge request. The commit changes only the draft's files: it adds and updates the selected files, removes ones the draft no longer has, and keeps unselected files. An updated file keeps its mode. It checks that the base branch has not moved, both before writing and before opening the review. A branch of the submission's name is reused only if it holds exactly this change, so a retry never proposes anything else under Astilba's name; one holding anything else fails the submission until you delete it. A retry reuses an open request only if it comes from the connected repository, so a fork's request from a branch of the same name is never taken for it. The Git source panel shows the newest submission's state, why it failed and a link to its review. An attempt the provider fails, rate-limits or doesn't answer is tried again, up to five attempts; a refusal, such as a moved branch or a credential without access, fails it at once. A failed submission can be submitted again with the same branch and review. Runtime secret-store values are checked against the names and contents of the files to submit and the contents of the imported baseline when you submit. A baseline file's name is not checked because it is already in the repository, so a draft can rename such a file away, although the review shows the old name. Surrounding whitespace in a stored value is ignored when at least 12 bytes remain, so `prod-key-123` followed by a newline also matches `TOKEN="prod-key-123"`. A shorter value with surrounding whitespace, or one of only whitespace, matches exactly as stored. Other values are also found URL-encoded and, from 12 bytes, with their lines indented or escaped, such as in a YAML block or a JSON string. A private key's armoured body, or a value that is one long run of base64, is also found rewrapped, commented out with `#` or, for a key, without its armour. Only a whole value or key body counts, so a line that ordinary files share, such as `NODE_ENV=production`, or a key's own public key or certificate, doesn't block them. This finds known values and isn't a scanner: other encodings and other parts of a value aren't recognised. Every stored version of a runtime secret counts, so rotating does not clear a match: change the file, or for imported content remove it at the provider and refresh. The files to submit are checked again before every attempt writes, because a value can become a runtime secret while a submission waits. If that check fails, or runtime secrets exceed its limit, the submission fails and nothing is written. The baseline is not rechecked because it is already in the repository, although a review that removes such a value still shows it. Runner submissions queued by an earlier version are stopped without any credential; submit those drafts again. Source files and plain configuration remain visible to workspace members and in exports; keep values in secret-version references.

Review and merge in the provider. The merge-triggered refresh checks the provider's merged-review state and exact merge commit before replacing a submitted draft. Another remote change preserves the saved draft and marks a conflict. Explicit refresh requires the current revision and an acknowledgement before discarding a pending draft. Changed Git files cannot produce a deployment plan before they are imported from the authoritative branch. Runtime variables and secret references remain platform settings; editing those does not require a Git commit. Accepted merged imports retain the submitted paths and current entrypoint selection, including when runtime settings were saved again after submission. If several reviews contain the same files, any matching review merged at the current branch head can authorise refresh. A GitLab project that merges by fast-forward makes no merge commit, so its squashed commit, or else the request's head, counts as the merge commit.

## Build and promote

Create a Git service, save it, then choose **Build a service**. The service can receive bindings and runtime configuration before its first build. Choose the branch, native target architecture, context directory, builder, runner and optional fallback. Dockerfile builds select a file relative to that context. Builds use the pinned BuildKit image and exact resolved source commit, even if the branch subsequently moves. Dockerfile remains the default, including when the API omits the builder. Railpack is an explicit alternative for the supported projects below.

Retry an accepted build request with its original `requestKey` to recover the same operation, even if the saved draft has advanced. A new build requires a fresh key and the current `baseRevisionId`. Retries still require current authorization and do not reconfigure the build target.

A build's note, such as why it failed or stopped, can quote its output, so an automation credential without `environment:read` gets a fixed note in its place (see [operation notes](automation.md)). Members and credentials holding `environment:read` see it as written.

Plain build arguments are public build inputs. Declared build-secret versions belong to a separate workspace store; runtime secret values are never hydrated into builds. Mount a declared secret using Dockerfile **RUN --mount=type=secret,id=NAME**. BuildKit keeps that mount outside image layers, but your Dockerfile can still copy or print its contents: only build trusted repositories, and avoid doing either. Known declared values and integration passwords are redacted from retained build output, including a value of at least 12 bytes printed without its surrounding whitespace, and URL-encoded forms. Known build/runtime secret values are rejected in public arguments before build admission, preview-policy persistence and runner delivery, matching on the same terms as source submission. Delivery checks current runtime secrets even when the build configuration was saved earlier. A rejected automatic target records its latest commit, bounded reason and time under **Git and builds**, without creating a build job or holding later pushes behind a permanent retry. Valid targets sharing the repository can still proceed. Database and provider failures remain retryable. Successful admission or configuration replacement clears the target's previous rejection.

If build inputs become invalid before the first runner delivery, a standalone build fails and releases the runner queue. A build or source operation cancelled or expired before its first delivery finishes on the controller, without reaching the runner. A command that may already have been delivered keeps its existing report and deadline handling, and its cancellation still reaches the runner with its frozen public arguments but no credentials; absence of an agent report does not prove it never ran. A runner receives an expired command as cancelled, whatever its clock reads. A preview build rejected before it is queued fails with that reason, and an environment created on that same pass is discarded, so it holds no resource slot. A build rejected after it is queued waits for a push, closure or its deadline to cancel it. Rejection messages do not include argument values, credentials or underlying service errors.

When upgrading to build delivery tracking, or to schema version 24 from an earlier one, stop and drain all old management processes before running the migration. Existing and imported runs, and runs unfinished before cancelled deliveries were recorded, have unknown delivery history and retain conservative reconciliation. Mixed old/new management processes cannot provide the never-delivered guarantee because old processes do not record delivery attempts.

A customer OCI registry receives a unique run tag and yields an immutable digest. Supply distinct repository-scoped push and read-only pull credentials. Build runners receive push access; assigned deployment agents receive pull access. Configured registry transfers require HTTPS. Without a registry, the image remains on its build runner and can deploy only on that server. Artifacts record commit, build input hash, architecture and local-host or registry identity.

**Promote an existing artifact** selects the same immutable image in another environment within the workspace. It preserves the destination's runtime variables, bindings, volumes and routes. It does not accept changed build inputs or rebuild the source. Reload the new saved draft and review a fresh deployment plan. Git-managed destinations still need their source review and merge. Deployment validates placement and architecture and pulls registry images by digest before replacing workloads. An older agent must be upgraded before it can advertise build capability.

Builds and deployment approval are separate by default. Authenticated pushes can opt a target into automatic builds. Automatic deployment requires an owner's explicit policy and a first interactive deployment. It uses the same image resolution, drift checks, stale-revision checks and apply admission as an interactive deployment, and the configuration it deploys is the applied configuration plus only this run's change: its built image or its imported source files. Targets in one environment build and deploy in turn. New host permissions, changes to services with persistent volumes or host-level access, a moved image tag on a service this run didn't change, any other saved draft change, including changed Compose entrypoints or another target's image left undeployed by a failed or blocked run, changed build inputs, a newer branch commit or removal of the owner's access block it. A draft change blocks it whoever saved it, including an owner's runtime variable, because nothing else in the draft has had a plan review. The build's image or imported source is still saved to the draft, unless the draft changed while it ran. Job history explains the block: prepare and apply a deployment plan to review everything in the draft, and the next push deploys automatically again. Previously reviewed unchanged permissions carry forward, including their binding address and target port. An omitted address keeps its own permission identity because [Docker default bindings can include IPv6](https://docs.docker.com/engine/network/drivers/bridge/#default-host-binding-address). Stateful service changes require an interactive plan: this includes effective variables and referenced configuration files, and a different resolved image behind an unchanged mutable tag.

A privileged or `cap_add` Compose service is held to the same rule, because it has host-level access to its server: approving it approved exactly what it runs. So is any service that shares a named volume or a network with one, because it can drive that service; a service that names no network, or that a route targets, is on the default network. Automatic deployment stops for review if a commit or build changes or removes such a service in any way, including its image, command, entrypoint, environment, the variables it interpolates, its bundled, bind-mounted or config files, secret versions, or how it is reached: its networks, volumes and routes, or if its image resolves to a different digest than the last reviewed deployment ran. An identical definition at the same digest deploys, and its approval carries forward with it. Published ports are the only permissions that carry forward for a service whose definition changes.

Every other service must also resolve to the same digest as the last reviewed deployment, unless this run changed it: the target a build promotes, or a service whose image reference the imported commit edits. A mutable tag such as `latest` that has moved since that deployment stops the automatic deployment, and job history names the service. Prepare and apply a deployment plan to review the new image. Pinning images by digest keeps their tags from moving under later deployments. Automatic source deployment can be disabled independently; resaving a build configuration controls that target's automatic policy. Automatic imports, builds and deployments run on the approval of the person who last saved or approved them, and pause when that person leaves the workspace, loses the role they need (an owner for imports and deployments, an owner or operator for builds) or changes their password, two-factor settings or recovery codes. The Git and builds section says why and offers **Approve as mine and resume**, which keeps the configuration and makes the approval yours; it resumes from the next push. See [when a member's authority ends](../services/platform/README.md#when-a-members-authority-ends). Job history records blocked decisions and the queued deployment operation. A build that the configuration cannot take, because it would go over the 128 KiB revision limit, become otherwise invalid, or need a Compose image line the file editor must change, still succeeds and keeps its artifact for manual promotion; its note says why it was not deployed. An import refused the same way fails with a note and leaves the draft as it was.

## Railpack builds

Select **Railpack** to plan and build a supported repository without a Dockerfile. The initial matrix is deliberately narrow:

| Provider | Validated project | Build and runtime evidence |
| --- | --- | --- |
| Node | Node with npm and a lockfile | Install, command overrides, declared secret and empty public argument during build; Node starts with the resolved version and no build secrets in its environment. |
| Go | A Go module producing a static binary | Compile with `CGO_ENABLED=0`, then start the resulting binary. |
| Shell | An explicit shell provider with a start script | Execute the build override and start script in the runtime image. |

Planning downloads a checksum-pinned `mise` from GitHub releases on the build server. It waits up to about five minutes for GitHub to respond, or half the time left in the assignment lifetime if that is shorter, then fails the build with a message naming the URL, and the build can be retried. A checksum mismatch is never retried. The Railpack images come from `ghcr.io`, and the build itself fetches language toolchains and packages from their usual sources, so a build server needs outbound access to those too.

The native fixture runs this matrix on Linux amd64 and arm64 in CI. Other languages, package managers, framework-specific adapters and arbitrary custom Railpack plans are outside this matrix; use a Dockerfile when a project exceeds it. A successful fixture is not a promise that every application in a language will build within the same budget.

The repository's `railpack.json` remains authoritative for other Railpack settings; JSON with comments is accepted. A public `RAILPACK_CONFIG_FILE` argument can select another context-relative configuration file. Optional **Build command override** and **Start command override** take precedence over repository commands without editing tracked source. The effective provider must be Node, Go or shell; unsupported explicit providers fail even when detection finds a supported language.

Railpack public arguments and declared build secrets become build-time environment inputs through BuildKit secret transport. They must have distinct names. `RAILPACK_` configuration settings must be public arguments. Planning receives public values and placeholder values for declared secret names; actual declared secrets are supplied only when executing build steps. Runtime and integration credentials are excluded from planning and build context. Build output uses the same bounded capture and redaction as Dockerfile builds. Trusted project commands can still copy secrets into their output, so avoid copying or printing them.

Each assignment freezes Railpack **0.43.0**, its matching frontend, builder/runtime image digests and the checksum-verified Mise **2026.10.14** planner helper for the native architecture. The prepared plan is saved in the encrypted agent journal before execution. Replay reuses that plan, including resolved tool versions, rather than redetecting against newer tool releases. Generated Mise installs and executable paths use those resolved versions. The BuildKit source policy rejects mutable image sources and pins Railpack's internal Alpine helper; custom image inputs require a SHA-256 digest. The pins live together in `internal/pipeline/railpack.go`. This does not freeze dependency registries, apt packages or arbitrary project downloads, nor guarantee byte-identical output.

Job history shows provider, planner/frontend version, prepared-plan hash and resolved tools. Builder mode, overrides and pinned inputs partition artifact identity and reusable caches. An older Dockerfile configuration retains its existing identity. Railpack requires a runner advertising the matching version after negotiating `Astilba-Agent-Railpack: v1`; install matching management and agent versions before selecting it. A downgraded runner cannot receive hydrated Railpack work, while credential-free cancellation remains available.

Railpack needs more storage than the small Dockerfile default. Selecting it visibly recommends **2 CPUs, 6144 MiB memory, 1024 MiB source storage, 4096 MiB builder storage and 30 minutes**; manually customized limits are preserved. The supported configuration floor is 256 MiB source and 3072 MiB builder storage. Tools, planner caches and source all count against the source tmpfs; the image archive must also fit after planner tools are removed. Choose limits for the application's actual size and runner capacity. Existing container memory, CPU, PID, storage, deadline, ownership and image-size limits also apply to planning and building. Railway's managed build service is not used.

## Monorepo watch paths

**Automatic build watch paths** accepts up to 16 distinct repository-relative files or directories, one per line. A directory includes all its descendants; matching is case-sensitive and does not interpret wildcards. Leave the list empty to watch every change. Paths are relative to the repository, independently of the selected build context. Include shared configuration, Dockerfiles and lockfiles when they affect the service.

Manual builds always run. An authenticated push still resolves and checks out the exact current branch commit. Before an automatic build, the runner compares that frozen commit with the last real successful artifact for the same application and compatible image inputs. It includes deleted paths and both sides of renames. Failed, cancelled or skipped work cannot advance this baseline. Missing history, an unavailable comparison or output beyond the comparison budget rebuilds conservatively. Changed build arguments, secret versions, context, architecture or other image inputs require a build.

When no watched path changed, history records a successful skipped job. It creates no image, promotion or deployment and never relabels the previous artifact with the new commit. Resource budgets, watch paths and automatic scheduling policy do not change an artifact's build-input identity.

## Budgets and recovery

Each workspace can retain 100 repository connections, 100 registry connections and 100 immutable build-secret versions, and queue at most 50 active pipeline operations. Work queues on the chosen runner when it is offline or busy. An explicitly configured eligible fallback may be selected at admission; an operation never silently moves to another host afterwards. A queued cancellation immediately releases the operation; executing work cooperatively cancels and removes only its matching owned runner container. Cancellation and deadline delivery do not require provider access or secret hydration, so a removed repository cannot strand a dispatched operation. An expired or cancelled result cannot publish an artifact. Changed recorded build inputs reject an obsolete result; newer branch commits block automatic deployment while existing immutable artifacts remain available for manual promotion.

Source operations have a 256 MiB tmpfs workspace and a 512 MiB memory limit. Builds default to two CPUs, 2 GiB memory, 256 PIDs, a 256 MiB source workspace and a separate 1 GiB BuildKit state budget. **Build resource limits** can select 1–8 CPU cores, 512–8192 MiB memory, 64–1024 MiB source storage, 128–6144 MiB builder storage and a 1–30 minute assignment lifetime. Source and builder storage are memory-backed and, together with 96 MiB reserved for tools, must fit the memory limit. These are hard container ceilings, not a reservation of host capacity; size them for the runner and its other workloads. Builds reserve at least 4 GiB of free space on the local Docker data-root filesystem. Local image archives are capped at 512 MiB and must also fit the workspace budget. Loading a local image may write at most 8 GiB to Docker's storage, and create at most 1,048,576 files and directories. It must leave 4 GiB and 262,144 inodes free on Docker's data-root and on `/var/lib/containerd` where present. The host's owner can change the size and the reserve on the agent; see [local image loads](agent.md#local-image-loads). The agent counts what Docker writes, not what the archive claims. That includes:

- archive members, with configs counted twice because Docker's legacy store writes them twice;
- every layer decompressed, with sparse files at their full size;
- every header byte, and the parent directories Docker creates;
- each layer again for every distinct chain of layers that includes it, with a fixed allowance for each unpacked layer's bookkeeping.

It streams the archive to Docker, holding each member's header until its size is counted and the archive's end until the whole image is. A refusal fails the stream, so Docker never imports a refused image. It also refuses archives it cannot measure:

- anything other than BuildKit's OCI layout;
- blobs that differ from their digest;
- manifests that name layers or documents the archive lacks;
- layers compressed other than with gzip or zstd;
- layers that read both as compressed and as plain tar;
- paths longer than Linux allows.

Registry builds are not loaded locally, and pulling them for a deployment is not bounded this way yet. Assignments expire after 30 minutes by default; a custom lifetime includes time spent queued and is frozen when the operation is created. Source operations retain their existing 30-minute lifetime. Custom budgets and watch paths require an agent advertising build-controls support. Older agents retain default Dockerfile builds; update them before selecting the new controls. New agents omit the capability extension until the controller advertises support in its `Astilba-Agent-Features` response header, keeping older controllers usable. A newly enrolled agent advertises build controls on its next heartbeat. Cancellation and expiry still reach an assigned agent that may hold the command without provider access or fresh credentials.

### Reusable layer caches

Cache-capable runners reuse local BuildKit layer-cache exports within one workspace/project. Compatibility includes the Git connection, branch, context, Dockerfile, architecture, build arguments, declared secret versions, selected builder and its pinned inputs. A different commit can reuse compatible layers; BuildKit still hashes the assigned source contents. A changed secret version starts a separate cache because BuildKit does not hash secret mount values. Cache hits are not guaranteed, and Dockerfile cache mounts are not persisted.

Each agent retains at most 128 MiB per archive, 256 MiB/eight archives per project and 1 GiB/32 archives overall, including one temporary archive. It evicts least-recently-used archives before reserving new storage and removes caches unused for seven days when a subsequent cache build accesses the store. Interrupted temporary archives are removed on the next access. Retention never prunes application images, database volumes or other Docker resources. Caches stay on their runner; fallback runners start cold unless they already have their own compatible cache.

Reusable caches require 256 MiB of spare memory after the configured source storage, builder storage and 96 MiB tool reserve. That memory backs a separate cache exchange; the configured BuildKit storage and container memory ceilings remain unchanged. Budgets without that headroom keep per-run state only. Export uses BuildKit's `max` mode to include intermediate layers, but oversized or unsuccessful exports are not retained. A missing cache or retention failure does not manufacture a successful build or deploy an artifact. Only locally successful builds can retain new layers; build errors and skipped work retain none. Promotion checks locally known cancellation and expiry. A later cancellation or management rejection can leave completed layers reusable; its artifact still cannot be deployed. Build results distinguish imported, absent and retained cache state; step logs show actual cache hits.

Caches are private files under the agent state directory and can contain source-derived data. They are not encrypted, exported with controller transfers or shared with another project. Build containers receive no host cache mount; bounded OCI-layout archives pass through Docker. Only trusted repository code belongs on a runner. New agents advertise `buildCache` only after the controller responds with `Astilba-Agent-Build-Cache: v1`; older agents continue with per-run caches, including queued assignments created before an agent update.

The native Linux arm64 Git/Dockerfile fixture measured 1.92 seconds cold and 1.54 seconds repeated, with its secret-consuming `RUN` layer reported cached. Other-project, changed-secret-version and changed-source builds execute that layer again; the frozen old commit remains reusable after its branch advances. These small-fixture observations include checkout and image loading and do not predict application onboarding or production build times.

The agent bounds captured tool output before parsing or redaction. Build stdout and stderr share a 1 MiB capture budget; exceeding it fails the build and discards the incomplete log capture. Complete captures are redacted before retaining the last 16 KiB, including when the build command fails. Source tools use smaller per-command limits where appropriate. Backup repository commands have a 1 MiB output cap; database metadata and upgrade inventory captures have a 64 KiB cap.

When the agent observes cancellation or expiry after a build command returns, it retains available redacted diagnostics without artifact fields. Cancellation does not make an image eligible for deployment. It does not reconstruct logs from stages that produced no captured output or from discarded overflow captures.

Checkout metadata and private auth files stay outside the build context. Initial build contexts reject symlinks and submodules. Failed fetches, failed uploads, cancellation and builder storage exhaustion do not mark an artifact applied or remove workload volumes. Completed artifacts are retained; cache/container cleanup does not prune deployment images or database storage.

The encrypted host journal records command inputs and outcome before acknowledgement. An operation becomes terminal only after its owned builder container has been removed. Cleanup failure reports **needs attention** for explicit local reconciliation; process interruption replays the running journal entry. Replays fetch the same commit and reconcile only the operation's owned container. Follow the [agent recovery procedure](agent.md) for an interrupted host. Key rewrapping covers Git access, registry access and build-secret versions as well as runtime secrets.

## Builder isolation

BuildKit runs rootless. Its container runs as host user 2000000000, which no host account has, with none of the host's capabilities except the two its `newuidmap` and `newgidmap` use to set up a user namespace. Each build step runs in that namespace as root, which is host user 2000000000; the step's other users are host users 2000000001 to 2000065536. The container's root filesystem is read-only, and it has no host devices, Docker socket or host data mounts. Docker's default seccomp profile applies, with only the calls BuildKit needs to create and mount inside its user namespace added. The agent's AppArmor profile, `astilba-builder`, denies the parts of `/proc` and `/sys` that Docker hides or makes read-only for other containers. Code that can mount, as an escape from a build step can, can still read their world-readable files by mounting `/proc` elsewhere, which any unprivileged user on the host can read anyway; the host's ownership of the rest keeps it unreadable and read-only. The agent never changes Ubuntu's restriction on unprivileged user namespaces, `kernel.apparmor_restrict_unprivileged_userns`: the profile allows them to the build container only.

So code that escapes a build step's sandbox, including a dependency's install script, is an unprivileged user in that container, not root on the host. It can't reach host devices, mount the host's disks, load kernel modules, change kernel settings, use the Docker socket, read other containers' environments or read the agent's state and credential. It can still read what its own build holds: the source, build secrets, the clone credential and, for a registry build, the push credential. The clone credential can't push when it is scoped as [Connect a repository](#connect-a-repository) lists: runners never receive the API credential or a write token. An escape can also reach what the [build network](#build-network) allows, and it can try to exploit the kernel through what a user namespace exposes, which is more than Docker's default allows. So treat a Build/Combined runner as trusted for the selected repositories and their dependencies, prefer a dedicated Build server to a Combined one, and don't give the runner's machine a cloud instance role or other credentials it doesn't need. A shared or Astilba-operated runner needs a separate virtual machine for every build, which this builder doesn't provide.

### Builder host requirements

The builder needs AppArmor enabled, as Ubuntu 24.04 has it by default, `apparmor_parser` from Ubuntu's `apparmor` package, and user namespaces, which `user.max_user_namespaces` or `kernel.unprivileged_userns_clone` set to 0 turns off. Before each build the agent loads its profile into the kernel, replacing any an earlier agent loaded, and confirms that the kernel enforces it. It writes nothing to `/etc/apparmor.d`: the profile stays loaded until the host restarts, and the next build loads it again. To unload it earlier, run `echo -n astilba-builder | sudo tee /sys/kernel/security/apparmor/.remove`.

A server without these reports builds as unavailable, with a note, and refuses a build it receives. A build never falls back to a privileged builder. Management sends builds only to agents that advertise the rootless builder, and refuses a build for any other runner with `runner.rootlessBuildsUpgradeRequired`; update its agent. Builds also carry a marker that an earlier agent can't account for, so one refuses a build instead of running it privileged, and management stops a build queued before the marker existed rather than send it. A current agent builds rootless for every build, so it still builds for a controller that predates the marker.

## Build network

Each build runs in its own network namespace on the agent's build network, `astilba-build-network`, whose bridge is `astilba-build0` and whose range comes from the agent's [container network pool](agent.md#container-networks). Before it creates each build container, the agent installs the build network policy, the nftables table `inet astilba_builds`, and reads it back. It applies to everything in the build container, including BuildKit's own requests for `ADD` URLs, Git contexts and base images, not only `RUN` steps.

A build reaches:

- public IPv4 addresses, such as package registries and Git hosts;
- the runner's DNS resolvers, on port 53 only. The agent gives BuildKit systemd-resolved's upstream servers, since builds can't use the loopback stub;
- its own Git provider and registry, on their ports, when they are on private addresses off the runner. A Git provider or registry on the build server itself isn't reachable from builds, and the build fails before it starts with a note saying so: use a separate host, or a public address that isn't the build server's;
- the private destinations the runner allows (see below).

A build never reaches:

- the runner itself, on any of its addresses, including ports Docker publishes there, whatever the runner allows;
- other containers on the runner, including services on a Combined server, whatever the runner allows;
- link-local addresses, which hold most clouds' instance metadata (`169.254.169.254`), Alibaba Cloud's metadata (`100.100.100.200`), Azure's host endpoint (`168.63.129.16`), loopback or multicast;
- private and shared ranges (`10.0.0.0/8`, `100.64.0.0/10`, `172.16.0.0/12`, `192.0.0.0/24`, `192.168.0.0/16`, `198.18.0.0/15`), which include the container network pool, the LAN, a VPC and private links;
- management's origin when it is on a private address, whatever the runner allows. A Git provider or registry that shares management's private address and port fails the build with a note saying so: give it its own address or port;
- anything over IPv6, including AWS's metadata at `fd00:ec2::254`. Builds use IPv4 only.

Docker translates no addresses for the build network: the policy does, after its rules. Without the policy, builds can't reach the internet. A rebooted host runs no build until the agent has installed the policy again. When the policy refuses a build's connections, the build log says how many packets it refused.

Builds leave with the runner's address. If management is on a public address, a build can reach it like anyone on the internet. So don't trust runner addresses at management's firewall, or at anything else's.

### Allowing private destinations

To let builds use a private package mirror or registry on your network, an owner adds it under **Build network** on the server's page. Each entry is an IPv4 address or range and a TCP port, such as `10.0.4.12:443` or `10.0.5.0/24:8081`, up to 32. Only private and shared ranges can be added: link-local addresses, loopback and multicast can't, and public addresses need no entry. An entry never opens the runner itself or its containers, even when its range covers their addresses, so a mirror for builds runs on another server. Saving needs the owner, recently signed in, and is audited. Removing an entry stops builds queued with it, including one the runner has started; replacing it with a range that still covers it does not. Every build on that runner can reach every entry, including code from its dependencies. The allowlist isn't part of a workspace export, so set it again after an import.

### Host requirements and firewalls

The policy needs nftables 1.0.9, which Ubuntu 24.04 installs by default and the bootstrap script installs if it is missing, and netlink access for the agent, which its systemd unit grants. A server without them reports builds as unavailable, with a note, and refuses a build it receives. Builds carry a marker that an agent predating the build network can't account for, so such an agent refuses them too, and management stops a build queued before the marker existed rather than send it. A current agent applies its policy to every build, so it still builds for a controller that predates the marker. Agent updates replace only the executable, so a host prepared with an earlier unit needs the permission added once:

```bash
sudo apt-get install --no-install-recommends nftables=1.0.9-1ubuntu0.1
sudo install -d -m 0755 /etc/systemd/system/astilba-agent.service.d
printf '[Service]\nRestrictAddressFamilies=\nRestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK\n' | sudo tee /etc/systemd/system/astilba-agent.service.d/build-network.conf
sudo systemctl daemon-reload && sudo systemctl restart astilba-agent
```

A host prepared for [cross-host networking](agent.md#optional-cross-host-networking) already has both.

A build server also needs Docker to write its firewall rules, as it does by default. The policy refuses the container networks that exist when a build starts, and Docker's own rules keep a build away from containers on networks created during it. With `"iptables": false` in Docker's configuration that second guard is gone, so such a server isn't supported for builds; the preflight warns when `/etc/docker/daemon.json` sets it.

Docker's forwarding rules come before ufw's, so builds reach the internet, their Git provider and allowed destinations on the LAN with ufw's `DEFAULT_FORWARD_POLICY="DROP"`. ufw's `deny incoming` also applies to builds' DNS queries to a resolver that listens on the runner itself, other than systemd-resolved's stub, which builds don't use. Such a resolver needs a matching rule: `sudo ufw allow in on astilba-build0 to any port 53`. The agent's policy still refuses everything else from builds to the runner.
