# Git and build workflows

Git source work and builds run on an enrolled **Build** or **Combined** runner. The management application contacts provider metadata APIs and schedules frozen commands; it never clones or builds locally. Deployment-only servers cannot receive pipeline work. GitHub, GitLab and Gitea use the same import, submission and exact-commit build workflow. Customer runners and registries work without an Astilba-hosted account.

## Connect a repository

An owner with recent authentication creates a repository connection under **Git and builds**. Choose GitHub, GitLab or Gitea, an exact provider origin, and the repository path. GitHub uses https://api.github.com internally; https://github.com is accepted at creation. Hosted GitLab and Gitea are supported directly. For other GitLab/Gitea origins, the management operator configures a comma-separated **ASTILBA_INTEGRATION_ORIGINS** allowlist. Explicit origins may reach private networks, so allow only trusted provider endpoints. HTTPS with publicly trusted certificates is required; numeric loopback HTTP is available only in local development.

Use a repository-scoped API/submission credential and a separate read-only clone credential for private repositories. GitHub needs repository metadata/content access and pull-request writes; GitLab needs project API and repository access; Gitea needs repository and pull-request access. The supplied account must be able to create a branch and review in the selected repository. There is no OAuth installation flow or SSH clone support in this milestone. Connections retain their repository identity and credentials rather than accepting a repository URL in each job. A repository ID or visibility change requires an explicit new connection; branch resolution and queued credential delivery recheck that identity.

The webhook URL and random secret appear once after creation. Configure **push** events in the repository, retaining the raw request body. GitHub and Gitea use HMAC-SHA256; GitLab uses its secret-token header and delivery identifier. Each delivery is checked against the connected repository ID. Delivery replay is deduplicated, retained delivery records are capped, and refresh jobs coalesce while active. Refresh resolves the current authoritative branch through the provider API, so an older delivery cannot roll the source backwards. Fork and pull-request events do not receive build credentials.

## Import and submit Compose

Create a **Compose files** environment and select the connection, branch, runner, optional fallback, entrypoints and supporting paths. The runner fetches the assigned commit and imports regular UTF-8 files, preserving their contents. The existing [Compose limits and runtime rules](compose-deployments.md) apply. Reload the current revision after a completed import; unsaved editor contents are never replaced automatically.

Save changes, then **Submit saved draft for review**. The runner creates one deterministic, create-only branch for that revision and one pull/merge request. It changes only the selected bundle files, retains unselected files and file modes, and checks that the base branch has not moved. A failed or cancelled attempt can retry the same saved revision without creating another submission branch or review. Runtime secret-store values are checked against both the imported baseline and edited files before submission and are not sent to the submission runner. Source files and plain configuration remain visible to workspace members and in exports; keep values in secret-version references.

Review and merge in the provider. The merge-triggered refresh checks the provider's merged-review state and exact merge commit before replacing a submitted draft. Another remote change preserves the saved draft and marks a conflict. Explicit refresh requires the current revision and an acknowledgement before discarding a pending draft. Changed Git files cannot produce a deployment plan before they are imported from the authoritative branch. Runtime variables and secret references remain platform settings; editing those does not require a Git commit. Accepted merged imports retain the submitted paths and current entrypoint selection, including when runtime settings were saved again after submission. If several reviews contain the same files, any matching review merged at the current branch head can authorise refresh.

## Build and promote

Create a Git service, save it, then choose **Build a service**. The service can receive bindings and runtime configuration before its first build. Choose the branch, native target architecture, context directory, Dockerfile relative to that context, runner and optional fallback. Builds use the pinned BuildKit image and exact resolved source commit, even if the branch subsequently moves. Dockerfile builds are the initial supported path. Railpack's spike demonstrated a narrow fixture; production Railpack support waits for broader validation.

Plain build arguments are public build inputs. Declared build-secret versions belong to a separate workspace store; runtime secret values are never hydrated into builds. Mount a declared secret using Dockerfile **RUN --mount=type=secret,id=NAME**. BuildKit keeps that mount outside image layers, but your Dockerfile can still copy or print its contents: only build trusted repositories, and avoid doing either. Known declared values and integration passwords are redacted from retained build output. Known build/runtime secret values are rejected in normal build arguments.

A customer OCI registry receives a unique run tag and yields an immutable digest. Supply distinct repository-scoped push and read-only pull credentials. Build runners receive push access; assigned deployment agents receive pull access. Configured registry transfers require HTTPS. Without a registry, the image remains on its build runner and can deploy only on that server. Artifacts record commit, build input hash, architecture and local-host or registry identity.

**Promote an existing artifact** selects the same immutable image in another environment within the workspace. It preserves the destination's runtime variables, bindings, volumes and routes. It does not accept changed build inputs or rebuild the source. Reload the new saved draft and review a fresh deployment plan. Git-managed destinations still need their source review and merge. Deployment validates placement and architecture and pulls registry images by digest before replacing workloads. An older agent must be upgraded before it can advertise build capability.

Builds and deployment approval are separate by default. Authenticated pushes can opt a target into automatic builds. Automatic deployment requires an owner's explicit policy and a first interactive deployment. It uses the same image resolution, drift checks, stale-revision checks and apply admission as an interactive deployment. New host permissions, changes to services with persistent volumes, changed drafts, changed build inputs, a newer branch commit or removal of the owner's access block it. Previously reviewed unchanged permissions carry forward, including their binding address and target port. An omitted address keeps its own permission identity because [Docker default bindings can include IPv6](https://docs.docker.com/engine/network/drivers/bridge/#default-host-binding-address). Stateful service changes require an interactive plan: this includes effective variables and referenced configuration files, and a different resolved image behind an unchanged mutable tag. Automatic source deployment can be disabled independently; resaving a build configuration controls that target's automatic policy. Job history records blocked decisions and the queued deployment operation.

## Budgets and recovery

Each workspace can retain 100 repository connections, 100 registry connections and 100 immutable build-secret versions, and queue at most 50 active pipeline operations. Work queues on the chosen runner when it is offline or busy. An explicitly configured eligible fallback may be selected at admission; an operation never silently moves to another host afterwards. A queued cancellation immediately releases the operation; executing work cooperatively cancels and removes only its matching owned runner container. Cancellation and deadline delivery do not require provider access or secret hydration, so a removed repository cannot strand a dispatched operation. An expired or cancelled result cannot publish an artifact. Changed recorded build inputs reject an obsolete result; newer branch commits block automatic deployment while existing immutable artifacts remain available for manual promotion.

Source operations have a 256 MiB tmpfs workspace and a 512 MiB memory limit. Build operations use two CPUs, 2 GiB memory, 256 PIDs, the same source workspace, and a separate 1 GiB BuildKit state budget. The cache is private to the run and removed at completion; step logs indicate cache hits within that build. Builds reserve at least 4 GiB of free space on the local Docker data-root filesystem, with additional reserve before loading local images. Local image archives are capped at 512 MiB and must also fit the workspace budget. Commands expire after 30 minutes. Larger builds need a future explicit budget configuration.

A runner uses privileged BuildKit and host networking. Treat a Build/Combined runner as a trusted host for the selected repository's build code, particularly when it shares a server with workloads. The builder receives no Docker socket, host data mounts or runtime secrets. Checkout metadata and private auth files stay outside the build context. Initial build contexts reject symlinks and submodules. Failed fetches, failed uploads, cancellation and builder storage exhaustion do not mark an artifact applied or remove workload volumes. Completed artifacts are retained; cache/container cleanup does not prune deployment images or database storage.

The encrypted host journal records command inputs and outcome before acknowledgement. An operation becomes terminal only after its owned builder container has been removed. Cleanup failure reports **needs attention** for explicit local reconciliation; process interruption replays the running journal entry. Replays fetch the same commit, reconcile only the operation's owned container, and reuse a deterministic submission branch/review. Follow the [agent recovery procedure](agent.md) for an interrupted host. Key rewrapping covers Git access, registry access and build-secret versions as well as runtime secrets.

## Verification

**make verify** runs provider API/signature contract fixtures, real PostgreSQL admission/background-policy journeys, browser journeys in Chromium/WebKit, and the earlier live disposable GitLab/Gitea spike fixtures. It does not imply a live hosted GitHub pass. **make verify-agent-host** additionally runs private Git HTTP import/submission, real BuildKit builds, a TLS Zot registry with separate push/pull policies, image-layer credential checks, cancellation and builder-only storage exhaustion. Native CI requires amd64 and arm64. The optional Cloudflare dashboard adapter forwards signed webhook bytes before static assets; no live Cloudflare deployment is needed for these local checks.
