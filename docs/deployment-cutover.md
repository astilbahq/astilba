# Inactive public web deployment preparation

Production still belongs to `astilbahq/docs` (Docs and apex) and `astilbahq/ui` (showcase). The [minimal activation preparation](deployment-activation.md) installs only a disabled manual forward workflow, creates no environment or credential, and enables no variable. Opening or merging it cannot deploy. Env publishing remains disabled; UI/Tokens publishing is retired. Old repositories remain unarchived and Cache #94 stays excluded.

`.github/workflows/deploy-web.yml` is the installed, manually triggered candidate. Actionlint, Zizmor and `pnpm verify:deployment` check it without deploying. `cutover.json` records all seven acceptance gates as false, including explicit runtime-security acceptance; `activation.mjs` rejects this checked-in policy even if someone sets its enable variable.

## Prepared deployment contract

| App | Verified assets | Existing route | Deployment working directory |
| --- | --- | --- | --- |
| Apex | `apps/site/dist` | `astilba.com`; exact `/docs` redirect | `apps/site` |
| Docs | `apps/docs/dist` | `astilba.com/docs/*` | `apps/docs` |
| Showcase | `apps/ui-showcase/dist` | `ui.astilba.com` | repository root |

The candidate accepts only manual main-branch dispatches in `astilbahq/astilba` while `WEB_DEPLOYMENTS_ENABLED == 'true'`. Build verification has no production credentials. It fetches complete history, installs the frozen workspace, runs existing UI/web source, browser and dry-run gates, and uploads three separate exact artifacts including hidden discovery files. Current Linux/Windows/runtime/security checks remain independent merge requirements.

The proposed `production-web` environment must require human approval before the deploy job starts. The deploy job rechecks acceptance after approval, downloads by the originating artifact IDs with digest mismatch treated as an error, validates complete assets and digests, and installs with lifecycle scripts disabled. It checks released Env availability and rejects stale main after the approval/install wait. It does not rebuild the static assets or call build-and-deploy package scripts. Credentials are scoped only to each Wrangler invocation.

The sequence is apex → apex smoke → Docs → complete web smoke → showcase → showcase smoke. Existing Worker names, configuration, bindings and route boundaries are byte-preserved. This is not an atomic three-app transaction: a smoke failure stops later steps but does not undo an earlier deploy. A reviewed partial-cutover recovery procedure is mandatory. The monorepo concurrency group serializes its own runs only; it does not coordinate with legacy repositories.

## Required before deployment enablement

1. **Content dates and source links.** Review and accept the [public content-history implementation and audit](content-history.md). Its manifest binds every imported public page to its original content fingerprint, UTC date and immutable public source commit; monorepo edits advance dates, traced pure renames retain them, and source actions point to the monorepo while HTML/Markdown retain original attribution. No private Handbook or Cache history is imported. For example, the imported Env overview last changed at public Docs commit `0a14681acaa76ca98d30bb182330d4603bb256e4`, not the October monorepo import. The acceptance gate remains false pending maintainer review; full-history checkout remains required and does not by itself prove the provenance audit.
2. **Artifacts and routes.** Compare all three candidate outputs with retained production artifacts and live smoke expectations. Enumerate and approve intended differences: monorepo UI source is 0.6.0 whereas the preserved legacy Docs bridge uses exact 0.5.0 bytes. Require unchanged redirect/route ownership, MCP/LLM/Markdown/skills discovery, headers, sitemaps, accessibility and existing screenshot assertions. Do not call the candidate byte-identical without a complete comparison.
3. **Protected environment and credentials.** Separately configure `production-web` with manual maintainer approval, main-only deployment rules and no administrator bypass. Decide self-approval explicitly for the sole maintainer. Add narrowly scoped production credentials only with approval; never copy their values into evidence. Verify the live protection and consuming workflow identity before enabling anything.
4. **Non-registry rollback.** Follow the [minimal cutover and provider-version rollback runbook](minimal-deployment-cutover.md). Capture and review each existing Worker's exact active version, verify provider retention and unchanged infrastructure, then bind that private baseline to the approved cutover. Test partial-failure controls without production writes. Provider rollback reselects retained code/assets without rebuilding or installing removed npm UI/Tokens. Fixtures are not proof of live provider acceptance; that limitation needs explicit acceptance before activation. Preserve existing source/archive evidence, but AWS backup provisioning and the offline image are not prerequisites for this path. Old workflow reruns are not rollback: retain their stale-main guard.
5. **Legacy handover.** Confirm no production run is in flight, then obtain separate approval to pause only old deploy entry points and transfer scheduled smoke ownership. Do not disable all legacy verification or change deployed routes merely to prepare this PR. A README-only merge to either legacy main can trigger deployment, so use the existing notices until that behavior is deliberately retired.
6. **Runtime security.** Complete the forward CLI and direct rollback runtime triage in [activation preparation](deployment-activation.md). The new `deploymentRuntimeSecurity` gate stays false; neither the parked image work nor clean lockfile scans clear embedded-library risks.
7. **Maintainer activation.** Obtain explicit deployment approval, record the accepted evidence, and review a separate enablement diff that updates only substantiated gates and adapts inactive-state tests to the approved contract. The enable variable must remain absent until then. Manually verify the approved current main, complete hosted checks/reviews and protected environment before first dispatch. Disable the deployment switch after the approved cutover window unless a different operating policy is explicitly accepted. No publishing enable flag changes with deployment activation.
