# Frontend development

The production dashboard lives in `apps/platform`. It uses React, TanStack Router/Query, Panda CSS and the generated OpenAPI client. Experiments remain separate. The rationale for the organisation is in [engineering principles](engineering-principles.md) and [agentic development research](agentic-development-research.md).

## Source boundaries

`src/router.tsx` composes routes, session gates and layouts. Features may use TanStack's public navigation components; they must not import our router instance or route definitions. Route-specific state is passed to a feature as typed inputs and callbacks. Shared session query options live in `src/api/session.ts`, alongside the API client.

Keep a feature's components, styling and private helpers together. A single file is sufficient until responsibilities merit a directory. Promote code to a neutral shared module only when another consumer needs it. Avoid a growing catch-all utilities directory or barrels that obscure dependency direction. Existing top-level feature files can move as they are substantially changed; a bulk rename is not a prerequisite for UI work.

`src/styles.ts` holds shared layout styles; new feature-only styles belong beside the feature. `src/theme.ts` supplies runtime theme state. The build-time theme lives in `theme/` and is consumed by `panda.config.ts`:

- `theme/tokens.ts`: primitive values and semantic roles, including light/dark values.
- `theme/global-styles.ts`: document defaults and shared accessibility rules.
- `theme/recipes/`: shared control recipes and their size/appearance variants.
- `src/components/`: native React control primitives backed by those recipes.
- `src/assets/`: source brand assets, including the original Astilba SVG lockup.

Generated `styled-system/` output is ignored by Git. `src/api/generated/` is generated from `contracts/platform`; do not hand-edit or format it.

## Signed-in workspace and Projects

`features/shell/app-shell.tsx` owns the desktop sidebar, mobile Base UI navigation dialog, workspace picker and account menu. `router.tsx` resolves the shared `workspace` search parameter against current session memberships and supplies `WorkspaceContext`; workspace sections consume that context instead of maintaining their own selectors. A missing parameter defaults to the first membership. An explicitly unavailable string ID shows a recovery state with a link that clears the selection. Account security remains reachable, and its drafts survive workspace changes. Application task state resets when the authenticated account changes. The GitHub OAuth callback stays in the authenticated AuthFrame because its authorization grant owns its workspace.

`features/projects` owns the project list and creation form (`projects-overview.tsx`), project loading/recovery and breadcrumbs (`project-frame.tsx`), the environment list (`project-detail.tsx`), and environment creation (`create-environment.tsx`). Loading, empty, failed-load/retry, unavailable and view-only states are distinct; request failures preserve creation drafts. Feature copy lives in the typed `projects` catalogue.

`/environments/new?workspace=…&project=…` is a separate page within the signed-in shell. It retains Visual, Compose and preview-template choices; success navigates to the created environment through the root route's workspace/project/environment search parameters. `workspace.tsx` composes `ProjectDetail` with an environment render callback and retains workspace import/create utilities. The environment feature owns the detail page and editor. Unsaved editor navigation uses the shared AlertDialog above mobile navigation; cancelling retains the drawer and draft, while completed navigation closes it and focuses main.

Shared query options stay below routing in `api/projects.ts` and `api/environments.ts`. Environment list keys use the workspace/project prefix and append the selected environment ID when opening an editor. Creation and preview mutations invalidate the prefix so both overview and selected-environment caches refresh.

The **Pages/Projects**, **Pages/Project detail** and **Pages/New environment** workshop scenarios use `workshop/app-preview.tsx` for the shell, memory routing and synthetic API fixtures. Detail states cover populated/empty lists, project and environment loading/recovery, unavailable selections, viewers, long names and navigation. Creation states cover all three configuration choices, validation, request/permission failures, submission, success and workspace changes. Shell and project catalogues participate in development pseudolocales; `workshop-tests/projects.spec.ts` checks light/dark layouts, mobile navigation and narrow RTL accessibility. Runtime journeys retain real-API coverage for workspace selection and environment editing.

## Environment detail

`features/environments/environment-detail.tsx` owns the environment heading, purpose/permission context, draft loading/recovery and local Overview, Configuration, Deployments and Settings tabs. Overview is the initial section; selecting a tab does not change the URL. `environment-overview.tsx` shows the saved revision, service inventory and deployment context before opening the editor. Saved services and runtime observations remain distinct: absent observations do not imply a healthy or running service. Saving a revision does not deploy it.

`environment-workspace.tsx` owns specification, saved-revision, conflict and layout-dirty state above the tab panels. Configuration retains the Visual/Compose editors, advanced specification and revision history; Deployments retains the existing pipeline, deployment, upgrade, backup and preview workflows according to environment purpose and permissions. Visited panels remain mounted while hidden, preserving drafts across local navigation. Route changes and browser exits still use the unsaved-change guard. `environment-settings.tsx` owns Secrets and owner-only automation controls; Settings remains accessible when the draft cannot load. Template owners also receive integration settings once the draft is available. Managed previews retain read-only configuration and secret controls.

`api/environment.ts` supplies the shared `EnvironmentPath`, draft and layout query options, and five-second `runtimeOptions` polling below routing. Keys include the workspace/project/environment path; list queries remain in `api/environments.ts`. Current revision writes publish through `publishDraft`, independently of whether an open editor can adopt them; historical comparisons never replace that cache. Successful layout writes cancel older layout reads and publish their canonical response. Initial draft failure offers contextual retry; failed background draft refreshes retain the loaded workspace and use the shared error toast. Runtime failures have their own recovery action without blocking saved configuration. Retry actions focus the relevant content region.

Configuration places Save and Reload above the editors and keeps historical comparisons separate from conflict recovery. Acknowledging a conflict updates the saved baseline while preserving local edits. Reload confirms discarding specification changes, retains canvas positions, and preserves newer edits made during its request. The volume-name field follows its authoritative name after reload while retaining unfinished input through unrelated renders. Read-only Compose content remains reachable and scrollable by keyboard.

**Pages/Environment detail** uses the real dashboard composition through `workshop/app-preview.tsx` and schema-typed handlers from `workshop/environment-fixtures.ts`. States cover Overview, runtime observations and drift, loading/recovery, permissions, environment purposes, Visual and Compose configuration, save/reload states, conflicts, revision comparisons, Deployments and Settings. Play functions exercise section entry, recovery focus and retained drafts after failed/conflicting saves. `workshop-tests/environment.spec.ts` covers light/dark desktop, mobile and narrow expanded RTL layouts, keyboard tab navigation, specification/layout retention and read-only controls. Real-API editor journeys cover reopening saved drafts and layouts, conflict acknowledgement, reload ordering and discarded volume names. The detail/overview and Configuration copy uses the typed `environment` catalogue and development pseudolocales; retained Settings and operational panel internals are not fully localised.

## Two-factor sign-in

After password verification, `/login` shows the authenticator challenge in `features/auth/mfa-challenge.tsx`. It shares the auth layout. Authenticator entry uses the shared `OTPInput` with six empty slots and the shared input recipe, a numeric keyboard, complete-code paste and one-time-code autocomplete. The explicit Verify action is followed by “Use recovery code”, then the quieter “Use another account” action. Keyboard order follows the same sequence. A separate recovery-code mode keeps one text input with its own label, instructions and validation. Both keep code text LTR and disable spelling/capitalization assistance.

Entering the challenge mounts a fresh form so the email cannot carry into the code input. Switching modes clears that mode’s form/error state and focuses the heading; language changes preserve the current form. Failed submissions retain the draft. Use another account logs out the pending session and reloads the current URL, clearing cached/in-flight session state while retaining the validated return destination. A failed initial session check uses the root’s existing connection-retry screen. Password reset and hosted signup remain on the initial sign-in stage.

`LinkButton` in `components/link` uses Base UI’s native button semantics with the shared link recipe for in-page actions. Use it for mode changes and cancellation; use typed `Link` for route navigation. It preserves neutral focus styling and disabled behavior.

## Password recovery

`/reset` asks for the account email and confirms the request without revealing whether the account exists. The email opens `/reset?token=…`; the typed route passes the token to `features/auth/password-reset.tsx`, which shows only the new-password field. The real API validates expiry and single use on submission. The only secondary action is “Back to sign in”; users can use the password recovery action there to request another reset email. The reset feature uses the shared auth layout and control recipes, retains failed drafts, and focuses the heading when it advances.

## Workspace invitations

The workspace invitation email opens `/invitation?token=…`; the sign-in page does not offer a separate invitation entry action. The typed route passes the token into `features/auth/invitation.tsx`; there is no code input. New accounts provide name and password, while signed-in accounts accept directly. Missing-token visits direct the user to their email. The sign-in return allowlist includes `/invitation` so an existing account can authenticate and return to the same token URL. Other auth routes, APIs and external destinations remain excluded. Hosted-beta signup and its separate invitation code are unchanged.

## Local commands

Use the Node, pnpm and Go versions pinned in the repository, plus a disposable local Docker daemon. From the repository root:

```sh
pnpm install --frozen-lockfile
export PLAT_APP_DOCKER_HOST=unix:///var/run/docker.sock
pnpm dev
```

Select your actual local Docker Unix socket; the example above is the usual Linux path. `pnpm dev` builds the Go API, starts pinned PostgreSQL on a free loopback port, applies migrations and starts the dashboard with hot reload at `http://127.0.0.1:54182/login`. Sign in with `owner@example.test` / `correct horse battery staple`; the initial workspace is **UI Sandbox**. This is a development-only account. Restart the command after changing Go code.

Local email is printed as plaintext in the `pnpm dev` terminal, including the recipient, subject and full body. Request a password reset for `owner@example.test`, then open the link from that output. The launcher explicitly selects console delivery and supplies a local sender; it sends no SMTP mail. Console delivery requires non-hosted development with a loopback listener and HTTP browser origin. Other environments retain SMTP delivery, with no console fallback.

`pnpm dev --port 55182` uses 55182 for the UI and 55181 for the API. Separate checkouts have separate databases; choose different ports and **separate browser profiles** when using them together. Browser cookies are shared across ports on `127.0.0.1`, so opening two previews in one profile replaces their sign-in sessions. Inherited `ASTILBA_*` configuration is cleared so the preview uses its own database and development settings. Stop it before `make verify`, whose browser fixture uses the default ports.

Ctrl-C stops the API, frontend and owned database container while retaining demo data. `pnpm dev --reset` deletes **this checkout's** demo database and seeds the same initial account/workspace. Generated credentials and keys stay in ignored, private `.artifacts/dev`; both Vite development servers deny HTTP access to `.artifacts`. Keep the state directory with its container: do not copy it to another checkout or remove the keyring from a database you intend to retain.

An atomic `.artifacts/dev.lock` prevents two launchers from changing the same database. If a forced kill leaves it behind, inspect `launcher` for the parent PID and ports, and `processes` for child process-group IDs. Use `ps` and a port-listening tool to establish which recorded processes still belong to this launcher (PIDs may have been reused). Stop those owned groups, confirm the old API/UI listeners and launcher are gone, then remove **only** `.artifacts/dev.lock` and restart. A dead parent PID alone does not prove its children stopped. Normal Ctrl-C removes the lock automatically.

The package's `prepare` hook generates Panda's types during installation. If lifecycle scripts were disabled, run `pnpm --filter @astilba/dashboard prepare` explicitly. For a frontend-only process against an already running local API, use `pnpm --filter @astilba/dashboard dev`; its defaults remain UI 54182 / API 54181. See the application setup guide for running the packaged service.

```sh
pnpm --filter @astilba/dashboard check
pnpm --filter @astilba/dashboard lint
pnpm --filter @astilba/dashboard format
pnpm --filter @astilba/dashboard format:check
pnpm --filter @astilba/dashboard check:fix
pnpm --filter @astilba/dashboard build
```

`check` regenerates Panda types, runs Vite+'s format, lint and type checks, then checks translation types, copy and catalogues. `format` writes formatting and organises imports; `check:fix` also applies safe lint fixes. The root `vite.config.ts` owns shared Oxlint/Oxfmt settings. Each app's Vite config owns its plugins, server and build settings. Generated code, build artifacts and source brand assets are excluded from formatting. Runtime import cycles are errors; erased `import type` references are allowed.

Vite+ replaces Biome and the separate frontend Vite/type-check commands. It is installed locally and pinned, so no global installation is required. `vite` is aliased to the matching `@voidzero-dev/vite-plus-core`; the Vitest override matches Vite+'s bundled runner. The narrow pnpm peer exception for that core alias accounts for its different version number. Keep all three pins aligned when upgrading, while preserving the release-age gate. This follows the [local installation](https://viteplus.dev/guide/local-cli) and [monorepo](https://viteplus.dev/guide/monorepo) guides.

Oxlint enables TypeScript-aware checks, React and accessibility rules. Explicit security rules retain the previous checks against raw HTML injection, unprotected blank-target links and script URLs (including non-JSX string usage). React Compiler-specific ref, purity and effect-state restrictions are not enabled because the app has not adopted the compiler. The tag-over-role preference is also disabled: our live status containers and labelled SVGs deliberately use ARIA. Rules for accessible names, roles, keyboard interaction and hook usage remain enabled, alongside the real-browser accessibility checks.

Panda, Playwright and Node's existing domain-test runner remain in place. Go retains `gofmt` and `go vet`; Wrangler still packages Cloudflare Workers. pnpm remains the package manager, and the existing Make targets still orchestrate the full application.

Existing `make check-app` invokes the dashboard check, and `make verify-canvas` invokes the canvas check, so both use Vite+ in the existing CI gates. `make verify-app` adds the production build and real API/browser journeys with disposable PostgreSQL; follow the root instructions for its Docker requirements. Tests covering navigation or authentication belong in the existing Playwright suite.

## Panda CSS conventions

The setup follows the [Panda Vite guide](https://panda-css.com/docs/get-started/vite): `@pandacss/vite` precedes React in `vite.config.ts`, generates styles and watches for changes. Both presets are explicit; `jsxFramework: "react"` enables extraction of recipe variants from React component props. There is no extra PostCSS integration or separate CSS watcher. `src/global.css` declares the standard layer order; the plugin supplies the generated stylesheet.

Use semantic colour roles (`fg`, `surface`, `border`, `brand`, etc.) in UI code so light and dark themes stay aligned. Add raw palette values to the token definition, not repeated component styles. `strictPropertyValues` rejects invalid enumerated CSS values, and `strictTokens` requires tokens for token-backed properties. Shared spacing, typography, sizes and radii use the Panda scale or named theme tokens. A bracketed raw value is an explicit exception for a one-off effect; do not use it to bypass the token system.

Use logical properties: `marginBlockStart`, `paddingInline`, `inlineSize`, `borderInlineEnd`, and `textAlign: "start"`. Vite+ extends Panda's `no-physical-properties` rule with the shared logical-property policy for production component styles, and the `logical-properties` Panda plugin rejects physical properties in global styles and recipes at config loading. These checks run through the existing `check`/`lint` commands. The vendor adapters use logical dimensions; CodeMirror's cursor border remains a physical library geometry override.

Panda's official lint plugin is loaded through the local `oxlint-panda.mjs` wrapper so the root and package commands resolve the same app config. It also checks token paths, raw colours, invalid nesting, extraction and missing source coverage. The JSX accessibility rules map our primitives to their native elements.

Follow Panda's [recipe guidance](https://panda-css.com/docs/recipes/overview): start with `css` for a one-off style, use colocated `cva`/`sva` when a component needs variants, and promote shared design-system recipes into configuration when they have real reuse. Keep style values statically extractable; select complete style objects rather than construct class names or token strings dynamically. Use CSS variables for values known only at runtime.

The [cascade-layer rules](https://panda-css.com/docs/styling/cascade-layers) matter: unlayered CSS outranks Panda's layers. React Flow and CodeMirror adapters intentionally remain scoped, unlayered CSS beside their components so they can override the libraries' styles. Keep that exception limited to vendor internals; ordinary app styling belongs in Panda. The adapters use Panda's token variables rather than a second palette.

Choose named scenarios in the sidebar to open validation errors, rejected requests, pending submissions, recovery mode and completed flows directly. Storybook's play functions reach these states through the actual forms and interactions. Canvas controls select light/dark/system, English, expanded or RTL pseudo, and viewport sizes. Existing page controls remain interactive. Workshop preferences belong to its separate origin.

Use the actual shared components and page features, and keep fixtures out of their imports. The sign-in route passes its validated return destination into `features/auth/sign-in.tsx`; stories never bypass production route guards.

Audited journeys select Storybook's manual a11y mode so the addon and Playwright do not scan concurrently; normal workshop browsing retains automatic scans. Story sweeps use the addon's body-level component scope, including portals, with a narrow exception for Base UI's empty focus sentinels ([maintainer explanation](https://github.com/mui/base-ui/issues/4668#issuecomment-4306200868)). The unsaved-change real-API journey excludes only empty WebKit inside sentinels and checks focus wrapping in both directions, keyboard cancellation and draft retention. The standalone auth and real API/PostgreSQL journeys retain their full-page audits and authentication/session checks.

## Inline auth validation

`Form validation={authValidation.signIn}` opts a form into Base UI’s Form/Field validation. Sign-in/MFA, both reset forms, invitation acceptance, hosted signup and explicit email verification use it; other Form callers retain native constraint validation, including raw controls outside Field. Migration is explicit because disabling browser validation on an unregistered native control would lose its validation.

`components/form-validation.ts` adapts synchronous Zod schemas to Base UI validators. Synchronous checks block submission; API requests stay in the existing mutation path. Field renders Base UI Label/Error with the shared recipes, keeping PasswordInput’s reveal button and label action order intact. Base UI owns invalid state, descriptions, first-invalid focus, submit-first timing and revalidation. Native constraint failures use the same schema-generated messages as custom rules. Server field errors are stable memoized maps, clear on edits, and use the same inline presentation. Sign-in credential errors use a persistent toast; link errors retain contextual form alerts. Form also accepts render-prop children receiving the current form-error message, so a flow can place it beside its controls without marking those controls invalid. Preserve drafts on all failures.

Auth validation lives in `features/auth/validation.ts`. `useAuthValidation()` builds schemas with the current `auth` namespace through `features/auth/messages.ts`; `createAuthValidation(messages)` accepts complete messages and named interpolation functions. Do not use global Zod locale configuration, concatenate translated fragments, or classify server errors by English text. Error codes select messages. Locale changes update visible messages without resubmitting, moving focus, or restoring server field errors that Base UI already cleared.

`FormValidation.errorFields` maps field-specific API error codes to their controls when the response does not supply field names. MFA and recovery verification map rejected credentials to the code field, using the same inline error, accessible description and first-invalid focus as client validation. `isRequestFailure` classifies transport, rate-limit and unexpected failures for toast feedback. Other forms keep their existing error presentation.

New passwords count Unicode code points (15–128) rather than HTML/JavaScript UTF-16 length. Passwords are submitted verbatim; the client does not trim or normalize them. Sign-in checks presence only, so a new-password policy does not block existing credentials. The Go API/OpenAPI contract remain authoritative; Zod provides early feedback rather than a security boundary. Add focused browser coverage for validation/focus/draft behavior and real API outcomes when migrating further forms.

## Localisation

The dashboard uses i18next and react-i18next. `src/i18n/instance.ts` initializes the bundled catalogues before React mounts; `provider.tsx` aligns the HTML language/direction and Base UI DirectionProvider. The provider does not key or remount the route tree. English is the only released locale and fallback. Current catalogues are small enough to preload; no network translation service or runtime catalogue fetch is involved.

Copy lives in `src/locales/en/common.json` (shared controls/root states), `auth.json` (authentication, hosted signup and email verification), `account.json` (account security), `app.json` (signed-in shell), `projects.json` (project/environment lists and creation) and `environment.json` (environment detail/overview). Keep namespaces feature-sized. The environment page structure and overview are migrated; retained workspace/editor, Settings and operational panel internals still include untranslated copy. Other dashboard feature copy, billing, backend emails and API prose remain outside the current migration. Routes and token/return destinations remain unchanged; language is not a URL segment or query parameter.

In development, the globe beside Appearance offers English, Automatic, Pseudo (expanded) and Pseudo (RTL). Pseudo adds accents and expansion while preserving interpolation and component placeholders; RTL additionally exercises logical layout and Base UI positioning. It is an English-based test locale, so HTML language remains `en`. Locale choice persists under `astilba-locale`; blocked storage only limits persistence. Automatic currently resolves to English, since that is the only released language. Development variants require explicit selection and are excluded from production assets and selection. Production hides the language menu until a second released language is available.

Use `useTranslation("auth")` or `useTranslation("common")` with typed selectors, for example `t(($) => $.signIn.title)`. Keep complete sentences in one message. Use named interpolation and i18next plural forms with `count`; use i18next's built-in Intl formatters for dates and numbers when those features migrate. Do not translate user content, credentials, API keys or machine identifiers. Emails and one-time codes use LTR inputs; free text uses automatic direction. Isolate embedded identifiers with `bdi` in rich messages. Pass opaque user content as literal React children through a self-closing named component, not through `Trans` interpolation: the latter can reinterpret interpolation syntax inside an otherwise valid email.

Use `Trans` only for rich text, with the current hook's `t` and an explicit components map. Typed route destinations stay in code; small wrappers accepting only `children` prevent translation attributes from overriding a link target. No `dangerouslySetInnerHTML`. React escapes interpolated values; the i18next `escapeValue: false` setting avoids double escaping and is for this React rendering boundary only.

After changing a catalogue run `pnpm --filter @astilba/dashboard i18n:types`, then `check`. The official CLI generates `src/i18n/generated/resources.d.ts`; do not hand-edit or format it. The module augmentation checks selector keys and supplied interpolation arguments. The pinned selector overload permits omitting the entire options argument, and the CLI interpolation rule currently checks string-key calls only; review selector interpolation arguments explicitly. `i18n:check` verifies generated freshness, statically detectable missing keys, interpolation, translatable JSX in migrated files and non-empty English fallback copy. Router/hosting currently mix migrated auth and unmigrated dashboard code, so they are excluded from hardcoded-copy lint, but remain included in key extraction and TypeScript checks. Keep new migrated features in their own files so lint coverage can grow without suppressions.

To add a real language, add complete feature catalogues, locale metadata (native display name, language tag, direction), resource registration and the CLI locale list together. Extend Automatic resolution to match browser preferences against released locales only. Do not expose a partial language as supported. Browser journeys cover live client/server error translation, retained drafts, storage failures, RTL keyboard menus, long text at 320px and production pseudolocale exclusion. The fixture runs both the packaged app and the Vite development server against the real disposable API.

## Shared controls

Import primitives directly from `src/components/button`, `button-link`, `input`, `password-input`, `select`, `textarea`, `checkbox`, `label`, or `link`. They preserve native DOM props, events and React 19 refs. Use `Field` and `BusyButton` from `src/ui.tsx` when form error association or submission feedback is needed. Field’s `labelAction` renders after the complete input, including PasswordInput’s reveal button, so related actions do not interrupt consecutive fields in tab order. Its recipe uses a wrapping flex layout to place the action beside the label when space permits, on its own line above the control when it does not. CSS ordering preserves the input-before-action DOM/tab order, and errors remain below the control.

```tsx
<Button variant="primary" size="md" type="submit">Save changes</Button>
<Button variant="secondary" type="button">Cancel</Button>
<Button variant="danger" type="button">Delete project</Button>
<Field name="email" label="Email" type="email"
  placeholder="you@example.com" autoComplete="username" />
<Label htmlFor="region">Region</Label>
<Select id="region" name="region">...</Select>
<Link to="/login" search={{ returnTo: "/servers" }} variant="plain">Sign in</Link>
<ButtonLink to="/environments/new" search={{ workspace: workspaceId, project: projectId }}>
  New environment
</ButtonLink>
<Anchor href="https://example.com" target="_blank" rel="noreferrer">Documentation</Anchor>
```

`PasswordInput` composes the shared Base UI-backed Input and ghost IconButton, inspired by [Chakra’s password input](https://chakra-ui.com/docs/components/password-input). It starts masked; the labelled Show/Hide button supports pointer, Enter and Space activation. Pointer activation preserves the input focus/selection, while keyboard focus stays on the toggle. Native value/defaultValue, change events, refs, names, autocomplete and error attributes reach the input. Spellcheck, autocorrection and auto-capitalization stay disabled when revealed. Password values are not copied into component state or persisted. The `passwordInput` slot recipe reserves logical end padding for the 40px target and 16px icon. Root hover sets the enabled input’s `--input-hover-border-color` to `control.interactiveBorder`, keeping the field highlighted over the reveal button. Input’s base border uses that optional override before the shared `control.border` idle colour, keeping the input highlighted across the whole control. Explicit focus/error/system-colour borders retain priority, and the existing border transition handles entry and exit. Use `Field inputComponent={PasswordInput}` to retain label/error association; login opts in, other password forms remain unchanged.

`OTPInput` composes Base UI’s OTP Field with a required `length`, the shared input recipe and size variants and an `otpInput` slot recipe for spacing and tabular digit alignment. Use a label targeting its `id`, or integrate it with `Field` through an input adapter as the authenticator screen does. Base UI owns the complete form value, validation, paste, autofill and roving keyboard focus. Later slots have localised position labels. Code slots and their arrow-key behavior stay LTR inside RTL pages through a scoped DirectionProvider. Automatic submission is off by default. Slots have no default placeholder and use the same border as other fields.

Button variants are `primary`, `secondary`, `danger`, and `ghost`. Input, PasswordInput, OTPInput, Select and Textarea share one border appearance, with no appearance variant. Control sizes are `sm` and `md`. `size` on Input/Select is the recipe size, not the native HTML character/row count.

Tune appearance in `theme/tokens.ts` and `theme/recipes/`, not route selectors. `control.border` and `control.interactiveBorder` own field boundaries; the interactive role is shared by hover and focus. Focus adds a 1px outline at zero offset to the 1px border without changing layout. Explicit `aria-invalid` errors retain the error edge; untouched required inputs do not appear invalid. Buttons use `action.*` and `destructive.*` roles, with a variant-matched focus ring. Disabled controls ignore hover; forced-colour and reduced-motion modes retain accessible states.

AuthFrame scopes the colour roles to the accepted auth palette. Recipes consume the same roles inside and outside authentication, and auth layout styles contain no input or button overrides. Checkbox remains a native checkbox with a shared recipe.

`Label` uses the label slot of the shared `field` recipe; `Field` consumes its root and header slots. This follows [Chakra's Field slot structure](https://github.com/chakra-ui/chakra-ui/blob/main/packages/react/src/theme/recipes/field.ts), with the existing grid spacing retained. Labels support both `htmlFor` and wrapping a control. Layout overrides such as checkbox rows remain explicit classes.

`Link` is the styled anchor passed to [TanStack Router's `createLink`](https://tanstack.com/router/latest/docs/framework/react/guide/custom-link), preserving route/search/parameter inference, refs, active state and navigation behavior. Use `Anchor` for external URLs, downloads and same-document anchors. Tooltip appearance uses `radii.full`, the menu’s `surface`/`fg` roles, `fontSizes.secondary` (13px), and `shadows.menu`. Keep tooltip content supplementary and non-interactive. `MenuRoot`, `MenuTrigger`, `MenuContent`, `MenuItem`, `MenuRadioGroup`, and `MenuRadioItem` provide shared dropdown parts. Menu and tooltip use Panda slot recipes, following [Chakra's menu anatomy](https://github.com/chakra-ui/chakra-ui/blob/main/packages/react/src/theme/recipes/menu.ts) with Base UI state attributes. The harmless preference persists under the existing `astilba-theme` key; earlier Light/Dark values remain valid. Blocked browser storage only limits persistence. Menu motion lives in the shared `menu` slot recipe. It adapts the supplied Transitions.dev scale-and-fade pattern to [Base UI’s animation lifecycle](https://base-ui.com/react/handbook/animation): `data-starting-style` enters from 0.97 scale, `data-ending-style` exits to 0.99, and `data-closed` disables pointer events. The popup’s `--transform-origin` follows Base UI positioning and viewport flips. `durations.menu.open` (250ms), `durations.menu.close` (150ms), and `easings.menu` own timing. Normal timings resume when the crossfade finishes. Pending preference and system changes are kept together so superseded callbacks cannot discard a manual choice. Initial rendering, unchanged resolved themes, reduced motion and unsupported browsers switch immediately.

Neutral `page`/`surface`, `fg` and `subtle` roles share the light/dark palette throughout the app, including auth aliases: #fdfdfd/#121212 backgrounds, #0d0d0d/#ffffff text, and #6c6c6c/rgba(202, 202, 202, 0.7) muted text. Action/contrast, feedback and field-border roles remain separate.

## Toast notifications

`components/toast.tsx` composes Base UI Toast with the Panda `toast` slot recipe. Mount `ToastProvider` once beneath the theme and locale providers; the application root and isolated Storybook canvas each do this. `useToast().add({ type, title, description, actionProps, timeout })` creates a notification. The viewport sits at the logical bottom/end, fits narrow screens, and shows at most three notifications. A padded scroll container keeps tall stacks reachable on short screens, and the notification region has its own visible focus indicator when reached with F6. The surface, text, lighter toast shadow, radii and 13px type use shared tokens. Motion adapts the supplied transitions.dev examples: `durations.toast.open`/`close` are 350/250ms, with the shared popup easing, a 16px single-toast rise (60px for an arriving stacked card), 2px blur and 0.97 entry scale. Older toasts peek by 12px, scale and fade by depth, and expand with an 8px gap on hover or keyboard focus. Base UI owns measured heights and expanded state. Cards share a fixed bottom anchor; a measured spacer reserves the collapsed or expanded stack height so scrolling remains available for different message heights. Entry transform is separate from the individual translate property used for stack geometry. Rear content is inert until expanded. Reduced motion removes transitions, decorative transforms and blur while keeping the instantaneous layout offsets. Default Base UI timing applies to ordinary notices; pass `timeout: 0` for persistent feedback. Reduced motion and forced colours follow the shared conventions.

`ErrorToast` owns one persistent notification per error source. A new failure creates or replaces it, clearing/retrying/unmounting closes it, and language changes update the existing message. Dismissed errors stay dismissed until another failure. Do not copy raw API text, credentials or tokens into a toast: use the typed message catalogue. Base UI supplies polite announcements, nonmodal keyboard access through F6, dismissal and focus restoration; creating a toast does not move focus. The close button and region names are localised. Swipe dismissal is disabled so vertical touch scrolling remains available.

Auth forms send connection, rate-limit and unexpected failures to ErrorToast. Sign-in also uses a persistent toast for incorrect email/password combinations; it preserves the draft and focus without marking either credential as individually invalid. MFA/recovery-code errors, expired links and field validation stay contextual. Reset and invitations share useAuthLinkCheck, checking URL tokens through POST /api/v1/auth/reset/validate and /api/v1/auth/invitations/validate before showing form controls. The bounded token travels in JSON; the endpoint returns no metadata, uses the existing CSRF/origin/no-store protection and a separate 60-check/15-minute per-IP budget, and does not consume or extend either link. Invitation checks create no account, membership or authentication state and expose no recipient/workspace details. Checking, invalid-link and unavailable-with-retry states are distinct. The query is memory-only, removed on unmount, and does not retry or refetch on focus/reconnect. Completion/acceptance still check expiry and consume their token transactionally, including the existing invitation account-binding rules. A link that expires or is revoked during entry produces an alert below the password field using the shared field error recipe; it does not invalidate the password. MFA cancellation failures also use it. A failed initial session load retains an “Unable to connect” heading and Retry connection button alongside its toast, so dismissing the message cannot leave an unexplained empty screen. Other dashboard notices retain their current presentation.

Toast motion is clipped inside the measured stack, with 12px inner padding and 4px viewport padding preserving the 16px outer inset. The extra 24px is included in the spacer height. This prevents entrance/exit transforms from briefly creating scrollbars, while the outer viewport still scrolls for genuinely tall stacks and the inner padding preserves shadow and focus clearance.

Browser tests use isolated loopback ports below the default ephemeral ranges:
15171 for Canvas, 15181–15189 for the real-API dashboard fixtures and 15201 for
the static workshop. The dashboard test's Vite instance uses 15182/15189; ordinary
`pnpm dev` retains 54182/54181 and `pnpm storybook` retains 54200. This keeps late
fixture listeners from competing with outgoing database sockets and lets browser
verification run beside the development previews.

## Hosted signup and email verification

Hosted beta invitation emails open `/signup?token=…`; the token is never a form field. `features/auth/signup.tsx` uses the shared auth layout, Base UI/Zod fields and typed catalogue. Availability, missing/invalid link, checking, retry, new/existing-account details and completion have separate workshop states. Existing accounts sign in with the invited address; existing-account MFA and workspace cohort admission remain server decisions. Final acceptance preserves drafts on failure and consumes the invitation only in the existing workspace transaction.

Verification emails open `/verify-email?token=…`. Sign-in (including MFA when enabled) preserves this return path. Verification is account-bound: the authenticated `/api/v1/auth/email/validate` checks without consuming, and the explicit Verify email button calls `/api/v1/auth/email/verify`. No page load verifies an address. Missing/expired links offer a new email; resending replaces the prior link. Account security embeds the same feature's request/completion content instead of a manual token form. Locale/theme changes preserve the current state; changing the account or URL token resets it.

Signup and email use `useAuthLinkCheck` alongside reset and invitations. Their checks return no recipient, workspace or token metadata; CSRF, origin and no-store protection remain in force. Signup checks have a separate 60/15-minute per-IP budget; email checks have the same independent budget per authenticated account, and their ephemeral query keys include that account. Final acceptance and verification remain authoritative if a link expires or is replaced after a successful check. Mail links use the configured installation origin, never a request-supplied host. The operator invite command validates this origin before issuing a link. Protected email-check authentication/CSRF failures refresh session state so an expired session offers sign-in again.

## Guided hosted onboarding

`/onboarding?workspace=…` identifies a specific owned workspace; signup returns its created workspace ID and replaces the invitation URL with this route. `features/auth/hosted-onboarding.tsx` derives the current task from session MFA/recovery confirmation and the subscription API's server-computed `managementActive`. It keeps account/workspace creation together, then guides authenticator setup, recovery-code saving and subscription. Existing completed steps are skipped. Workspace subscription settings provide a resume link; Continue later keeps normal project access and server-side admission rules.

`AuthenticatorInput` shares the six-digit OTP adapter across sign-in, enrollment and identity confirmation. Enrollment requires an explicit action. `RecoveryCodesConfirmation` is shared with account settings and acknowledges only the generation returned when codes were created. Account/version locks and a generation UUID prevent a stale tab from marking replacement codes saved. The acknowledgement does not renew recent authentication. New/replaced codes set `recoveryCodesSaved=false`; migration18 preserves legacy completion. Codes and setup keys remain component memory only. Reloading before confirmation offers regeneration, with recent identity confirmation when required. Language/theme changes preserve the current screen and drafts.

The subscription step displays the configured server allowance and sends users to provider checkout for price/payment review. No plan catalogue or price is invented. Checkout returns with `billing=returned` or `billing=cancelled`; neither marker grants access. Delayed webhooks have an explicit status refresh; unconfigured billing shows operator guidance. Typed routes and account/workspace keyed state keep resume, membership and account changes aligned.
