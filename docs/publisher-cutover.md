# Env and UI publisher cutover

Status: **prepared, not activated**. Development is canonical in `astilbahq/astilba`; publishing and deployment authority still belongs to the original repositories. This preparation creates no npm trust connections, environments, enable flags, tags, GitHub releases, npm publications or deployments. Cache, including private Cache #94, has no publisher path.

## Prepared identities

| Product | npm packages | Tag | Future workflow | Protected environment |
| --- | --- | --- | --- | --- |
| Env | `@astilba/env` | `env/vX.Y.Z` | `.github/workflows/release-env.yml` | `npm-env` |
| UI | `@astilba/tokens`, then `@astilba/ui` | `ui/vX.Y.Z` | `.github/workflows/release-ui.yml` | `npm-ui` |

The inactive templates live in `tooling/publishing/workflows/`. They require separate repository variables `ENV_PUBLISHER_ENABLED=true` or `UI_PUBLISHER_ENABLED=true`, exact public metadata, a clean checkout, and a tag pointing to the **current** monorepo `main`. Bare `v*`, cross-product tags, prereleases, root and Cache packages are rejected. UI preserves the published-GitHub-release trigger; Env preserves the tag-push trigger and creates its GitHub release only after registry verification.

Env reuses the entire existing package/consumer matrix and its source-bound archive verifier. A namespaced adapter retains the original GitHub release asset and retry checks. UI verifies its full existing source/browser/packaging contract, packs tokens and UI once, and transfers exact files with a source commit/tree, entry hashes/modes and a manifest digest supplied independently by the verification job. Only publish jobs receive OIDC permission. Both templates use GitHub-hosted runners, pinned Actions and Node 24.18.1 / npm 11.16.0; dependency installation uses pnpm 11.17.0. Publishing uses exact archives, public provenance and disabled lifecycle scripts, never a workspace-recursive publish or a long-lived npm token.

## Activation requires separate approval

Do not perform these steps as part of preparation. Activate one product at a time, in a reviewed PR and an explicitly approved first-release window:

1. Recheck old-repository release activity, registry versions and package-owner access. Env source/registry is 0.3.0; tokens/UI source is 0.6.0 while the observed registry version is 0.5.0. These are inventory observations, not permission to release those versions. Choose an unused version; do not republish or move old tags.
2. Update the relevant public manifests' `repository.url` to `git+https://github.com/astilbahq/astilba.git`, preserve the exact `repository.directory` (`packages/env`, `packages/tokens`, `packages/ui`), and update `homepage` and `bugs` to the values returned by `publisherMetadata()`. Preserve package names, exports, dependency policy and `publishConfig`. Reconcile the existing public-metadata tests, version checks, scoped guides and generated/versioned artifacts through an approved change; do not relax existing assertions just to activate publishing. Current metadata intentionally fails the new publisher guard.
3. Copy only the approved product template into its exact `.github/workflows/` filename. In the same activation PR, transition that product's preparation-state assertions in `preparation.test.mjs` and `identity.test.mjs` (inactive filename, phase and legacy-metadata rejection) to positive active-identity and permission tests; keep the other product's inactive assertions until its own cutover. The UI template runs this suite itself. Update release-authority guidance in the same activation PR. Preserve the complete required CI, reviews and security gates. Keep both enable variables absent until the release window; merging a template is not permission to publish.
4. Create the matching GitHub environment with required maintainer review, prevent self-review where supported, and disallow administrator bypass. Limit deployments to that product's `env/v*` or `ui/v*` tags, not branches or bare `v*`. Add separate tag rulesets for `refs/tags/env/v*` and `refs/tags/ui/v*` that prevent deletion and updates and restrict creation to the approved release maintainers. Confirm `main` protection remains active. Do not create a tag as a test.
5. An authenticated npm package owner reads back all existing trust connections and package publishing policy. Record their IDs and exact old bindings privately. Add the three applicable GitHub bindings from `tooling/publishing/trusted-publishers.json`, including **workflow filename and environment**, without deleting old publishers. Use direct publish permission only, not staged publishing. Confirm the readback rather than assuming an old CLI's one-publisher limit.
6. Only after explicit first-publication approval, pause the old product publisher, enable its new variable, create the approved immutable namespaced tag on verified current `main`, and perform that product's existing release trigger. No web deployment or Cache release accompanies this step. Recheck main/tag identity immediately before publishing after any environment wait.
7. Verify registry tarballs byte-for-byte, package/version identities, a clean consumer install, npm signature/provenance/publish attestations, and the signed provenance's exact monorepo, workflow, tag and commit. The registry verifier derives SHA-512 expectations from the already-verified archives, requires their manifest commit to match the release commit, and checks both signed attestation subjects against those exact bytes. npm verifies signatures before the identity checker reads those bundles. The protected GitHub environment and authenticated npm trust readback must independently match the product binding; npm's signed GitHub provenance payload does not contain an environment field, so the payload checker does not claim to verify it. Env additionally verifies both GitHub release assets by rereading and downloading them. Review any partial publication manually; never overwrite a version or move/reuse a tag. Tokens and UI cannot publish atomically: if tokens succeeds and UI fails, stop and choose a reviewed coordinated recovery/version rather than silently skipping an existing version.
8. After successful acceptance, revoke only the obsolete product publisher IDs, confirm token-based publishing is disabled, and remove any old temporary npm secrets without exposing them. Disable the old product's release workflow through its own reviewed change. Keep old repositories unarchived; release/deployment retirement is a separate decision.

[npm's current trusted-publisher guide](https://docs.npmjs.com/trusted-publishers/) permits multiple connections and says a new connection expires if it does not first publish successfully within **two days**. Add trust only inside the approved first-release window, not while these templates are inactive. [The npm trust CLI](https://docs.npmjs.com/cli/v11/commands/npm-trust/) requires package-owner write access and 2FA; older CLI documentation describes a single connection, so use authenticated current readback before changing existing trust. These packages already exist: no bootstrap token is needed. [npm provenance guidance](https://docs.npmjs.com/generating-provenance-statements/) requires the public repository metadata to match the publishing repository.

The preparation's read-only `npm trust list` attempts returned `E401` (no authenticated npm package owner on this machine). Existing live trust and publishing policy are therefore **not verified**, and were not changed. No credentials were read, copied or added.

## Stop and rollback boundaries

Before any publication, leave/remove the product enable variable and stop tag/release creation; old authority remains available until deliberately paused. Do not activate both old and new publishers for the same release. If a tag or GitHub release already exists, do not delete, retarget or recreate it to retry. Once npm accepts any archive, disable the new publisher and use a reviewed forward recovery; published immutable versions cannot be rolled back. Leave deployments and Cache #94 excluded throughout.
